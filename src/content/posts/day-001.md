> 安全学习的第一步不是学攻击，而是把实验环境搭好。这篇文章记录我从零搭一台 Kali 攻击机的完整过程：装 VMware、下预装镜像、配 Host-Only 隔离网络、验证连通性，最后把过程中卡住我的几个点逐条拆开讲。跟着做大概 1 小时能跑通，重点在第四节和第八节。

## 一、为什么要用虚拟机，还要用 Host-Only

虚拟机是一个沙盒：在里面怎么折腾都不会影响真实电脑，搞坏了删掉重建即可。这一点对安全学习尤其重要——你要跑扫描器、要打靶机、要故意制造异常流量，这些操作放在物理机上风险不可控，放在虚拟机里则完全可回收。

比虚拟机更关键的是网络模式。VMware 提供三种常见模式，选错会直接导致后面所有实验做不下去：

| 网络模式 | 能否上网 | 虚拟机之间互通 | 安全性 | 适用场景 |
| --- | --- | --- | --- | --- |
| NAT | 能 | 否 | 中 | 日常上网、查资料 |
| 桥接 Bridged | 能 | 是 | 低 | 需要真实 IP 的场景 |
| 仅主机 Host-Only | 否 | 是 | 高 | 渗透实验（本文采用） |

Host-Only 的价值在于：它让 Kali 和靶机处在同一个虚拟交换机上，彼此可以互相通信；但这个虚拟交换机没有连到真实网络，所以攻击流量不可能泄漏出去。一句话概括——先把自己关起来，再开始动手。

## 二、实验环境与验收标准

| 项目 | 内容 |
| --- | --- |
| 宿主机 | Windows 10 / 11 |
| 虚拟化软件 | VMware Workstation Player（个人使用免费） |
| 攻击机 | Kali Linux 官方预装虚拟机镜像 |
| 网络模式 | Host-Only（VMnet1），子网 192.168.56.0/24 |
| 预计用时 | 2–3 小时（实际约 1 小时） |
| 验收标准 | Kali 内 ping 192.168.56.1 能通 |

## 三、安装 VMware Workstation Player

从官网下载安装包，一路“下一步”默认安装即可，不需要改任何选项。安装完成后打开软件，能看到主界面就说明装好了。

下载地址：https://www.vmware.com/products/workstation-player.html

![图 1　VMware Workstation Player 主界面](/images/csdn/week01/Day001-1.png)

## 四、下载 Kali 预装镜像

Kali 官方除了提供 ISO 安装镜像，还提供已经装好的虚拟机镜像。强烈建议新手直接用后者——省掉分区、装系统、配引导的整个流程，解压就能开机。

下载页：https://www.kali.org/get-kali/ ，路径选 Virtual Machines → VMware 版本（.7z 压缩包），文件大小约 3–4 GB。下载完解压，会得到一个包含 .vmx 配置文件的目录。

> **提示** 解压后占用空间比压缩包大不少，建议提前确认磁盘剩余空间在 15 GB 以上。

## 五、导入并启动 Kali

在 VMware Workstation 中依次点击：文件 → 打开 → 选择解压目录里的 .vmx 文件 → 启动。首次开机会提示“我已复制该虚拟机”或“我已移动该虚拟机”，选“我已复制”即可（选移动会保留原网卡配置）。

Kali 预装镜像的默认登录凭据是固定的：

*默认登录凭据*

```text
用户名：kali
密码：  kali
```

![图 2　成功登录 Kali Linux 桌面](/images/csdn/week01/Day001-2.png)

## 六、配置 Host-Only 网络（关键步骤）

这一步是整个环境搭建的核心，也是最容易出错的地方。顺序很重要，请严格按下面五步走：

*VMware 配置步骤*

```text
1. 先关闭 Kali 虚拟机（改网络适配器必须在关机状态下，否则选项是灰的）
2. 编辑 → 虚拟网络编辑器 → 添加 Host-Only 网络（VMnet1）
3. 记下子网地址，例如 192.168.56.0
4. Kali 虚拟机设置 → 网络适配器 → 选“仅主机模式（Host-Only）”
5. 重新启动 Kali
```

> **注意** 第 1 步和第 5 步是一对：改硬件配置前必须关机，改完再开机。很多人在这里卡住，以为软件故障，其实是虚拟机还在运行。

![图 3　VMware 虚拟网络编辑器中的 Host-Only（VMnet1）配置](/images/csdn/week01/Day001-3.png)

## 七、验证网络是否配好

开机后在 Kali 终端依次执行下面两条命令：先确认 IP 落在 192.168.56 网段，再确认能 ping 通宿主机（宿主机在 Host-Only 网卡上的地址固定是 192.168.56.1）。

*验证命令*

```bash
# 查看 IP 地址，关注 inet 那一行
ip addr

# 测试与宿主机的连通性
ping 192.168.56.1
```

ping 的输出里看到 0% packet loss 就算通过。如果 ping 不通，先回第六节检查网络模式，不要急着怀疑系统。

![图 4　ping 192.168.56.1 成功，0% packet loss](/images/csdn/week01/Day001-4.png)

## 八、熟悉几条基础命令

环境通了之后，花十分钟把下面这几条命令敲一遍。它们是后面所有实验的操作基础，尤其是 ip addr 和 sudo，会反复用到。

*基础命令练习*

```bash
whoami            # 我是谁 → kali
pwd               # 我在哪 → /home/kali
ls -la            # 这里有什么（含隐藏文件）
cd /home/kali     # 切换到指定目录
ls /usr/share/    # 看看 Kali 预装了哪些工具目录
sudo apt update   # 更新软件包列表（可选）
```

![图 5　执行 whoami / pwd / ls -la 等基本命令](/images/csdn/week01/Day001-5.png)

| 命令 | 作用 | 示例 |
| --- | --- | --- |
| pwd | 显示当前所在目录 | pwd → /home/kali |
| ls | 列出目录内容 | ls -la 显示详细信息含隐藏文件 |
| cd | 切换目录 | cd /home/kali |
| whoami | 显示当前登录用户 | whoami → kali |
| ip addr | 查看 IP 地址 | 看 inet 那一行 |
| ping | 测试网络连通性 | ping 192.168.56.1 |
| sudo | 以管理员权限执行 | sudo apt update |

## 九、踩坑记录

下面六个坑是我和同学在实际搭建中最常遇到的，按“现象 → 原因 → 解决”整理：

| 现象 | 原因 | 解决办法 |
| --- | --- | --- |
| 虚拟机启动即报错，无法开机 | 宿主机 BIOS 未开启 CPU 虚拟化 | 重启进 BIOS 打开 Intel VT-x / AMD-V |
| Kali 里 ping 不通任何地址 | 网络模式选错，或不在同一网段 | 确认选 Host-Only，且双方都在 192.168.56.0 网段 |
| ip addr 显示 10.x.x.x 或 NAT 地址 | 网络适配器仍挂在 NAT 上 | 关机后重新选择 Host-Only 适配器 |
| 想改网络模式但选项是灰的 | 虚拟机处于开机状态 | 先关机再修改硬件配置 |
| 进不去系统，忘记密码 | 预装镜像凭据固定 | 默认账号密码都是 kali |
| 镜像解压或导入失败 | 磁盘空间不足 | 清理磁盘或换到空间充足的分区 |

### 坑 1：虚拟机开机就报错

这是最容易被误判成软件问题的一个。实际原因是宿主机 BIOS 里没开 CPU 虚拟化，VMware 拿不到硬件虚拟化能力，虚拟机自然起不来。进 BIOS 把 Intel VT-x（或 AMD-V）打开即可，注意有些笔记本还需要同时关掉 Hyper-V。

### 坑 2：改网络适配器时选项不可点

我一开始想当然地在开机状态下改网络适配器，结果设置项全是灰的，改不了，当时还以为是 VMware 装坏了。后来才明白：虚拟机的硬件配置必须在关机状态下才能修改。这类“顺序性”的坑，看教程时完全不觉得是问题，只有自己动手才会卡住。

### 坑 3：ping 不通，但 IP 看着是对的

有一种情况很迷惑：ip addr 显示的地址确实在 192.168.56 段，但就是 ping 不通宿主机。常见原因是 VMware 虚拟网络编辑器里 VMnet1 的子网和虚拟机实际拿到的地址不一致（比如编辑器的子网是 192.168.88.0）。解决办法是回到虚拟网络编辑器核对子网地址，必要时让虚拟机重新获取一次 DHCP 地址。

## 十、小结

- 预装镜像省掉了装系统的漫长过程，真正的门槛是网络配置，不是安装。

- Host-Only 是渗透实验的标准选择：虚拟机互通、不上互联网、流量不外泄。

- 所有“改硬件配置”的操作都必须在关机状态下进行，这是最容易忽略的前提。

- 验证顺序应该是：先看 IP 是否在同网段，再 ping 网关，最后才怀疑其他环节。
