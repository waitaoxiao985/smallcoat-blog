> 网站上线后，最容易被搜索引擎收录、又最不该被外部看到的，是目录列表、备份文件、配置文件这类本不该出现在 Web 根目录下的内容。这篇文章从运维自检的角度出发，讲清四个检索运算符的用法、三类常见信息暴露的判断依据，以及发现问题后如何下线和整改。所有检索目标都是自己的站点。

## 一、为什么从搜索引擎自检开始

安全自查分两类。一类是直接对自家资产发扫描请求（漏扫、目录探测），会产生日志、可能触发 WAF；另一类是借助第三方已经采集公开的数据做反向检索，也就是「我的站被别人看到了什么」。

后者特别适合两类场景：一是新接手一个站，不清楚历史上传过哪些文件；二是排查运维疏忽导致的信息暴露。搜索引擎的索引相当于一份「外部视角的资产清单」，能直接告诉你哪些路径已经被公开抓取。

这一步的产出是风险清单，不是操作手册。看到可疑路径时，正确的动作是记录、核实归属、然后下线，不涉及任何交互尝试。

> **说明** 本文所有检索都对自己的测试站点与公开示例域名进行，仅做只读查看，不对任何非授权资产发起请求。

## 二、四个核心运算符

搜索引擎的高级运算符有几十个，做信息暴露自查真正高频的只有四个。

| 运算符 | 作用 | 典型用法 | 自查时的关注点 |
| --- | --- | --- | --- |
| site: | 限定站点或子域 | site:example.com | 该域下有哪些页面被收录，是否存在废弃域名 |
| filetype: | 限定文件类型 | filetype:pdf | 是否存在本应内部流转的文档 |
| inurl: | URL 中包含指定字符串 | inurl:admin | 管理后台路径是否暴露在索引中 |
| intitle: | 页面标题包含指定字符串 | intitle:"index of" | 是否存在开启了目录浏览的目录 |

### 2.1　site: 限定范围

site: 的作用是「只在这个域里搜」，把结果收敛到自己的资产上。

*基础用法*

```text
site:example.com
site:example.com 后台
site:*.example.com
```

第三种写法是关键——它会连带检索所有子域名。实际排查中，主站往往做得很干净，出问题的却是历史遗留的测试环境、旧版门户、内部工具，而这些系统常常还挂着一个没人记得的子域名。

### 2.2　filetype: 找非网页文件

Web 根目录下最不该公开的，是各种非 HTML 文件：备份、配置、日志、数据导出。

*按文件类型检索*

```text
site:example.com filetype:pdf
site:example.com filetype:xls
site:example.com filetype:doc
```

正常业务文档被收录，本身可能不算漏洞，但如果里面有内部通讯录、报价单、组织架构，就构成敏感信息暴露。判断标准是「这份文件的外泄会造成什么后果」，而不是「它是不是被索引了」。

### 2.3　inurl: 定位功能页

inurl: 匹配的是 URL 路径部分。管理后台为了好记，路径通常起名很直白：admin、manage、login、console、phpmyadmin。

*定位后台与接口*

```text
inurl:admin
inurl:login
inurl:phpmyadmin
inurl:api
```

对自查来说，这一条的价值在于发现「后台路径已经公开」。管理入口暴露在搜索结果里，等于把爆破目标直接标出来。整改方式不只是改路径（改了照样能被扫到），更关键的是加访问控制、限制来源 IP、启用多因素认证。

inurl:api 这一条对前后端分离的站点尤其值得查——接口路径如果出现在索引里，要确认这些接口本身是否做了鉴权。

### 2.4　intitle: 抓目录浏览页面

Apache、Nginx、IIS 在目录下没有默认首页文件时，会启用目录索引，页面标题固定是 Index of /。这个特征非常稳定。

*目录浏览检索*

```text
intitle:"index of"
site:example.com intitle:"index of"
```

这是自查里命中率很高的一条。开启目录浏览本身是配置项，但它把该目录下所有文件名都列了出来——如果目录里放着压缩包、SQL 文件、临时上传物，风险会立刻放大。

## 三、组合检索：三类高频信息暴露

单个运算符只能定位，组合起来才能判断问题的性质。下面三类是排查中遇到最多的。

### 3.1　目录浏览未关闭

*目录浏览 + 父目录特征*

```text
site:example.com intitle:"index of" "parent directory"
```

加上 "parent directory" 是为了排除标题里恰好含 index of 的正常页面。结果里目录名、文件名会被完整列出，相当于把一部分文件结构公开了。

在自己的测试站点上就复现出了这种情况，整个目录的文件名一览无余。整改方式很直接：在 Web 服务器配置里关掉目录索引（Nginx 的 `autoindex off`、Apache 的 `Options -Indexes`），再把该目录下不该存放的文件清走。

![图 1　检索到的目录浏览页面（已关闭目录索引）](/images/csdn/week02/Day008-1.png)

### 3.2　配置文件与备份文件遗留

*配置文件与数据备份*

```text
site:example.com filetype:conf OR ini OR env
site:example.com filetype:sql OR bak
```

前一类是配置：.conf / .ini / .env，里面通常写着数据库连接串、第三方密钥、内网地址。后一类更严重——.sql 是数据导出，.bak 是备份，这两类文件如果落在 Web 目录下又被收录，等同于整站数据公开。

排查时的处理顺序是：先确认文件是否真的可访问，再确认内容敏感级别，然后立刻从 Web 目录移走，最后清理索引缓存。仅靠 robots.txt 拦不住已经被人下载走的部分。

### 3.3　管理入口暴露

*后台入口检索*

```text
site:example.com inurl:login OR inurl:admin
```

搜到后台地址只是第一步，排查动作到这里就停——只记录 URL、页面标题、收录时间，不做任何登录尝试。判断「后台暴露」这个风险项成立与否，不需要靠试密码来证明。

## 四、公开的检索式库：别人的经验清单

安全社区长期维护着一批公开的检索式集合，从 2002 年积累到现在有几千条，按类别整理好：敏感目录、错误信息、泄露文件、登录入口、网络设备等等。

它的用法应该反过来看——不是「拿它去翻别人」，而是「拿它当检查清单，看自己的站有没有中招」。这相当于一份现成的暴露面清单，按目标系统类型逐条比对，比自己从零想查什么要全面得多。

![图 3　公开检索式库的类别列表](/images/csdn/week02/Day008-3.png)

### 4.1　三类值得优先自查的风险面

*对应自查项*

```text
phpinfo 探针页面
wp-config 配置文件的文本备份
版本库目录 .git 的可访问性
```

第一类是探针页面。phpinfo.php 是 PHP 环境信息页，很多站点装完忘了删，页面里写着系统版本、扩展列表、绝对路径、甚至数据库连接信息。自查方法：直接访问自己的 `/phpinfo.php`，能打开就说明要删。

第二类是配置文件的文本备份。以 WordPress 为例，wp-config.php 正常不会被当文本读取，但有人为了备份复制成 .txt 放在同目录，就变成可直接下载了，里面有数据库账号密码。自查方法：检查站点根目录有没有多余的 `.txt` `.bak` `.old` 副本。

第三类是版本库目录。.git 目录一旦能被 Web 直接访问，完整的提交历史和源码就暴露了，历史提交里还常有硬编码的密钥。这是实际事件中出现频率很高的一类问题，自查方法：访问自己的 `/.git/config`，返回 200 就说明没做拦截。

三类的共同整改思路一致：生产环境不部署这些文件，部署了就在 Web 层拦截路径，并定期用自动化检查固化成巡检项。

## 五、自查优先级：先查自己

这套方法最该先用在自己身上。按下面的顺序排一遍，投入产出比最高。

*自查三档*

```text
第一档：site:你的域名 filetype:sql OR bak OR env
第二档：site:你的域名 intitle:"index of"
第三档：site:你的域名 inurl:admin OR inurl:login
```

第一档处理数据泄露，一旦成立影响最大；第二档处理文件结构暴露，整改成本最低；第三档处理入口暴露，通常需要配合访问控制而不是只改路径。

发现不该公开的页面后，处理路径是：先从服务器侧移除或加拦截（这解决根本问题），再在 robots.txt 里加 Disallow 防止后续被重新抓取，最后用 Google Search Console 的「移除网址」工具把已收录的记录下线。注意 robots.txt 只是「请求不抓」，对已经存在于索引里的页面无效，必须走移除工具。

## 六、踩坑记录

| 现象 | 原因 | 解决办法 |
| --- | --- | --- |
| 检索页打不开 | 用的是境外搜索引擎，当前网络环境访问不了 | 换用国内可直接访问的搜索引擎，site:、filetype:、inurl:、intitle: 语法同样支持 |
| 弹出验证码 unusual traffic | 短时间请求过多被判定为自动化流量 | 放慢检索节奏，间隔几秒再搜；或换搜索引擎 |
| site: 返回 0 条结果 | 该站未被收录，或写成了子域 | 改用 site:*.example.com 连带查子域；换引擎交叉验证 |
| 差点顺手点进搜到的后台 | 好奇心想验证一下 | 只记录 URL，不访问。访问即越界 |

### 坑 1：以为是语法写错了

第一次检索时页面一直转圈，第一反应是运算符写错了，反复改检索式。后来才意识到是搜索引擎本身访问不通。

排查顺序应该是先确认「搜索引擎能不能正常用」，再谈语法。这类问题最省事的处理方式就是换一个当前网络环境下可直接访问的搜索引擎——site:、filetype:、inurl:、intitle: 这四个运算符在主流引擎上的行为基本一致，对自查来说完全够用。

### 坑 2：查几次就弹验证码

连续快速检索会触发反自动化机制，页面变成「我们的系统检测到您的计算机网络中存在异常流量」，要求选图验证。

处理办法很简单：放慢。每次检索间隔几秒，别开着脚本猛刷。真被拦了就等十几分钟再试，或者直接换搜索引擎。这也是被动检索的一个隐性限制——节奏得听平台的。

### 坑 3：site: 一条结果都没有

对着一个域名写 site:example.com，返回 0 条。原因不是语法错，是这个站压根没被收录——新站、纯内网站、或者加了 noindex 的站都会这样。

改法：一是用 site:*.example.com 试子域，很多时候主站没收录但某个子域被收录了；二是换搜索引擎交叉验证，不同引擎的收录范围差别很大。

### 坑 4：差点越界

搜到自己测试站的后台登录页时，手指已经在点链接了。这里必须踩住刹车——自查阶段的产出是「一张 URL 清单」，不是「一次登录尝试」。

给自己的规矩：查到的每一个入口，只记录 URL、页面标题、收录时间，不做任何交互。验证「后台是否需要加固」这件事，交给站内的权限配置检查去做，不需要从外部试。

## 七、小结

- 四个运算符覆盖大部分自查场景：site: 限范围、filetype: 找文件、inurl: 定位功能页、intitle: 查目录浏览。
- 组合比单用强：site + intitle 查目录索引、site + filetype 查配置和备份、site + inurl 查管理入口，三类各有明确整改动作。
- 公开的检索式库当检查清单用，比当工具用价值更高——按系统类型逐条比对，不容易漏项。
- 这套方法完全被动，目标侧零感知，但也因此受限于搜索引擎的收录范围，**搜不到不等于不存在**，它只能作为漏扫和人工核查的补充。
- 自查优先于其他一切：先把自己的暴露面清干净，成本远低于事后应急。
