> 这一篇不学新东西，做四件复查的事：给一段过滤规则，判断它有几处缝隙；给一段前端代码，找出 Source 到 Sink 的路径；把两处薄弱点拼成一条链；最后把这一周的掌握程度诚实地记一遍。检验的方式不是「能不能做出来」，而是「能不能说清为什么」。

## 一、先读规则，再动手

练习给的过滤规则大致是这样：先把输入整体转成小写，再依次删掉五类固定字符串——脚本的开始标签、结束标签、两个最常用的加载类事件、一个弹窗函数名，最后把结果拼进页面输出。

*过滤规则的结构（示意，非原文）*

```text
步骤 1：把输入统一转成小写
步骤 2：依次删除固定字符串（开始标签、结束标签、两个事件名、一个弹窗函数名）
步骤 3：把处理结果拼进页面的一个容器里输出
```

读完这段，判断顺序应该是固定的：先看它「在哪一层判断」（字符串层还是语法层），再看「删除是几趟」，最后看「名单覆盖了多少」。三项看完，缝隙自己就浮出来了。

## 二、逐条判断：哪几处能被利用

| 过滤点 | 实现方式 | 判断 |
| --- | --- | --- |
| 统一转小写 | 先把输入转小写再处理 | 大小写变形全部失效 |
| 删除开始/结束标签 | 一次性替换，不回头复查 | 可以利用：拆成两段、中间嵌一段会被删掉的内容 |
| 删除两个事件名 | 只列了两个具体写法 | 可以利用：事件是开放集合，未列出的照样生效 |
| 删除弹窗函数名 | 只删这一个名字 | 可以利用：同类函数、或把名字拆开动态拼接 |
| 拼进容器输出 | 直接当 HTML 写入 | 根本问题在这里：写 HTML 的内容会被解析 |

这张表最重要的一行其实是最后一行。前面四行说明「名单不全」，最后一行说明「方向上就错了」——只要输出仍然被当 HTML 解析，名单补多少条都只是抬高成本。

## 三、两处可利用点，机制各是什么

第一处是「删除只做一趟」。把关键字拆成前后两段，中间嵌一段会被删掉的内容，删除之后两侧正好拼回原样。这不是什么技巧，而是「替换不递归」的必然结果。

第二处是「名单只列了两个事件」。能执行脚本的不是标签，而是事件属性；事件是一个开放集合，而且有很多是不需要用户交互就会触发的。只封两个名字，等于没封。

| 机制 | 为什么会成立 | 怎么补 |
| --- | --- | --- |
| 替换不递归 | 删除后不复查拼出来的新内容 | 循环替换到稳定，或改用白名单 |
| 名单式封事件 | 事件集合远大于名单 | 不靠名单，一律输出编码 |

> **这里的关键判断** 判断一段过滤有没有用，不要问「它删了什么」，要问「它判断的是字符串还是语义」。判断字符串的，永远只是抬高成本；判断语义的（输出编码、白名单净化），才是关门。

## 四、第二题：一段前端代码里的 Source 与 Sink

练习给的是一个搜索页：从地址栏取出查询参数，用参数构造结果区的内容。整条链路在浏览器里完成，服务器全程不参与。

| 环节 | 在这段代码里的位置 | 判断依据 |
| --- | --- | --- |
| Source | 从地址栏读查询参数 | 值来自用户可控的地址 |
| Sink | 把内容写进结果容器的 HTML | 写入方式会解析标签 |
| 触发 | 页面加载即执行 | 不需要任何额外交互 |

为什么判定它是纯前端的：这段内容根本没有作为请求参数离开浏览器。所以在服务端日志里查不到，只有从前端代码或者浏览器调试里才能发现。

| 错误写法 | 为什么错 | 改法 |
| --- | --- | --- |
| 把参数写进 HTML 容器 | 写 HTML 会解析标签 | 改成写纯文本 |
| 把参数拼进脚本求值 | 字符串就是代码 | 改成解析数据格式 |
| 把参数拼进地址跳转 | 可构成脚本型协议 | 先校验协议，只允许安全协议 |

## 五、第三题：把两处薄弱点拼成一条链

题目给了一个带令牌的后台改权限接口，同时给了一个有存储型注入的评论功能。单看两个问题都不致命：一个是「别人没法替你发请求」，一个是「页面会被注入脚本」。拼起来就完全不同了。

*一条链的五个环节（示意）*

```text
第 1 步：把带脚本的内容提交到一个会被他人浏览的位置（内容进了库）
第 2 步：管理员打开这个页面，脚本在站点自己的源下执行
第 3 步：脚本读取同源页面，把表单里的令牌读出来
第 4 步：用读到的令牌构造一次正常的表单提交（改权限）
第 5 步：目标账号的权限被改动，整个过程管理员没有任何操作
```

第 4 步有个细节值得注意：为什么用表单而不是脚本发请求？因为表单提交不受跨域预检的限制，也不需要读取响应，只是「把请求发出去」，比脚本请求更省事、更不容易被拦。

如果这条链成立，日志里只会看到管理员自己的浏览器发了一次合法请求。这就是「链路问题」比「单点问题」更难查的原因：每一跳单独看都正常。

## 六、五个判断点，收成一张表

| 判断点 | 要问的问题 | 答错的后果 |
| --- | --- | --- |
| 入口 | 内容从哪来，谁可控 | 漏掉整类输入 |
| 解析层 | 这段内容最终被谁解析成什么 | 把「过滤了字符串」当成「安全了」 |
| 执行位置 | 脚本在哪一方的浏览器里跑 | 搞错危害范围与定级 |
| 权限边界 | 能操作的对象属于谁 | 把越权误判成正常功能 |
| 可观测性 | 这条链在日志里留下什么 | 查不到，也无法证明修复有效 |

## 七、Week 7 的复盘

| 主题 | 核心结论 | 掌握度 |
| --- | --- | --- |
| 绕过基础 | 过滤判断字符串，浏览器判断语义 | 熟练 |
| 绕过进阶 | 常见标签封住后，换解析器、换协议、换事件 | 基本掌握 |
| DOM 型 | Source 到 Sink，服务器可以不参与 | 熟练 |
| 请求伪造 | 三个条件：自动带凭据、只认凭据、无需确认 | 熟练 |
| 令牌 | 值要校验、不可省略、绑定会话 | 熟练 |
| 浏览器接管 | 危害边界从页面扩到内网 | 待加强 |
| 综合 | 把单点问题看成链 | 完成 |

- 最有用的一条：判断过滤要看实现，不能只看名单。一次性替换意味着可以拼合还原。

- 最容易忽略的一条：两处中危拼起来是高危。评估时不能逐个打分再取最大值。

- 最需要补的一条：浏览器接管之后的内网行为，还缺少一套自己的观察方法。

## 八、踩过的坑

| 坑点 | 症状 | 原因 |
| --- | --- | --- |
| 只验「能弹窗」 | 误判成低危 | 没继续验证同源可读，导致影响被低估 |
| 以为过滤后就是安全的 | 复查时才发现可拼合 | 没读实现，只看了名单 |
| 表单与脚本请求混用 | 预检被拦 | 跨域脚本请求有额外限制，表单更简单 |
| 只测一处输入 | 漏掉整类入口 | 输入位置没有按「所有可控字段」列全 |

## 九、小结

- 一段过滤规则的可利用点，永远来自「它的判断依据」与「浏览器的解析规则」之间的差。读实现比试写法省时间。

- 前端问题也可以用同一套框架分析：入口、解析层、执行位置、权限边界、可观测性。五个点答全，结论才站得住。

- Week 7 的主线是「让别人的浏览器替我做事」。理解了这条主线，防护的优先级自然就清楚了：先堵注入，再限制执行，最后降低凭据价值。
