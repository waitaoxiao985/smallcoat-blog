> 前三天讲的全是「把脚本塞进页面」，利用发生在浏览器里。今天转向另一条线：把文件塞进服务器。很多人以为文件上传的危险在于「能传上去」，其实真正的危险在于两个条件同时满足——文件被存到了某个位置，而这个位置又允许被执行。本篇就在本地靶场上把这两个条件一个个确认清楚。

## 一、实验环境与本次目标

| 项目 | 内容 |
| --- | --- |
| 靶场 | 本地搭建的测试靶场 |
| 测试模块 | File Upload |
| 安全级别 | Low |
| 本次目标 | 确认上传后的存放路径，并判断该路径是否可执行 |
| 边界 | 仅在本机靶场验证，只执行只读命令，验证完即删除文件 |

*验证上传风险的标准动作只有三步：传一个无害文件摸路径、传一个只输出固定内容的文件看解析、最后用一条只读命令确认执行。到这一步就够了，再往下就是另一类问题了。*

## 二、第一步：先传一张正常图片，把路径摸清楚

先传一张普通的 jpg 图片。该靶场的页面上传成功后，会显示一行提示，里面带着文件的相对路径——这个路径是整个验证过程中最需要记下来的信息。

*路径就是这样确认的*

```text
上传成功后的提示（示意）：
 [上传目录]/demo.jpg

浏览器实际访问的地址（示意）：
 http://[靶场地址]:8082/[上传目录]/demo.jpg
```

为什么要先传图片？因为图片一定不会被拦，能顺利走完整个上传流程，从而暴露真实的存放目录。这一步不涉及任何危险动作，但产出的信息量最大：上传目录在哪、对外能否直接访问、文件名是否被重命名。

> **这里的关键判断** 上传点的风险等级不取决于「能不能传」，而取决于「传上去的东西会被怎么对待」。如果上传目录只允许静态读取、一切脚本都不解析，那么传什么都只是占地方；反之才叫危险。

## 三、第二步：确认这个目录会不会解析脚本

知道路径之后，做一个最小验证：传一个后缀为该站点后端语言的文件，内容只输出一句固定文字，然后访问它。如果页面显示的是那句文字，说明文件被当成程序执行了；如果显示的是文件源码，说明没解析；如果是一堆乱码或下载提示，说明根本没按文本处理。

*第二步：解析验证*

```text
文件内容（只输出一句固定文字，不含任何其他语句）：
 <?php echo 'upload-check'; ?>

访问结果对照：
 显示 upload-check      → 文件被解析执行，上传目录可直接执行代码
 显示 <?php echo ...   → 未解析，源码被原样返回，风险较低
 直接下载 / 乱码        → 未按文本处理
```

这三种结果里，第一种是真正的问题所在。它说明服务器把用户提供的文件当成了可执行程序——从这一刻起，「上传一个文件」等价于「在服务器上留下一个可以随时调用的入口」。

## 四、整条链的三个环节

把上面两步串起来看，一个上传点从「能传」到「能用」需要三个环节同时成立。任何一环断掉，威胁就大幅下降。

| 环节 | 成立条件 | 断掉之后 |
| --- | --- | --- |
| 文件被接收 | 服务端接受该文件（格式、大小、类型检查通过） | 根本进不来 |
| 文件被访问 | 上传目录对外可访问，或路径可被猜到 | 传上来也调不到 |
| 文件被执行 | 上传目录允许解析脚本，且后缀未限制 | 只能当静态文件下载，无法执行 |

这三个环节里，第一环是最容易被当成全部的一环——很多站点把精力全放在「后缀检查」上，结果第二环和第三环敞开：目录对外可访问、解析配置默认开启。真正有效的做法是在第三环上关门，也就是让上传目录不可执行。

## 五、为什么「只查后缀」总是不够

如果防护只做后缀检查，那它面对的是「有限的黑名单 vs 无限的写法」这个老问题。下面这几种情况，都属于同一个思路在不同层面的表现，列出它们不是为了给出绕过方案，而是为了说明为什么校验必须落在「允许什么」上。

| 检查依据 | 为什么总会有缺口 |
| --- | --- |
| 文件名结尾的字符 | 同一个执行语义往往对应多个后缀，黑名单列不全 |
| 客户端声明的类型字段 | 该字段由客户端提供，服务端不应采信 |
| 文件名中间的后缀写法 | 多重后缀、大小写、尾随符号等写法差异 |
| 文件开头几个字节 | 在合法开头字节之后追加内容即可 |
| 前端脚本的提示 | 请求可以不经浏览器直接发出，服务端必须独立校验 |

共同点很清楚：它们判断的都是「这个东西像不像坏东西」，而坏东西的写法可以无限变。白名单的判断是「这个东西是不是我要的那一种」，只要名单足够窄，未知的东西就进不来。

## 六、校验应该落在哪一层

把防护拆成四层，按有效性从高到低排列。前三层是服务端的事，最后一层是架构层面的事。

| 层次 | 做法 | 效果 |
| --- | --- | --- |
| 执行层 | 上传目录关闭脚本解析，只作为静态文件目录 | 最根本，即使传进来也不能执行 |
| 名称层 | 服务端强制重命名为随机串，后缀由服务端指定 | 切断「用特定名字访问」的路径 |
| 内容层 | 按真实内容类型（而非声明的类型）判定，白名单放行 | 防止伪装格式混入 |
| 隔离层 | 文件存到独立域名或独立存储，与主站分离 | 即使被执行也无法接触会话与主站数据 |

> **四层的关系** 执行层决定「能不能跑」，名称层决定「找不找得到」，内容层决定「进不进得来」，隔离层决定「跑了能碰到什么」。只做其中一层，等于只锁了一扇门。

## 七、上传点还要注意什么

- 重命名策略：服务端生成随机文件名，原始文件名只存数据库用于展示，不参与路径拼接。

- 存放位置：不要放在 Web 根目录下可执行的位置；条件允许则存到对象存储或独立域名。

- 大小与数量限制：限制单文件大小与并发数量，防止占用磁盘。

- 权限最小化：运行 Web 服务的进程不要有写入其他目录的权限，也不要用高权限账号运行。

- 删除与保留策略：临时文件定期清理，避免历史文件长期暴露。

- 记录留存：上传时间、来源、原始文件名、存储路径都要记日志，事后排查靠它。

## 八、自查清单

- 找到站点所有上传入口（头像、附件、导入、编辑器插图），逐个确认校验在服务端完成。

- 对每个上传点，传一张普通图片，记下返回的存储路径，确认该路径对外是否可直接访问。

- 确认存储目录是否配置为不解析脚本——这一条比任何后缀检查都有效。

- 确认服务端是否强制重命名，原始文件名是否参与路径拼接。

- 检查上传目录的权限与 Web 进程的权限，确认最小化。

*上传点的验证一定要留下确切路径。报告里只写「上传成功」等于没写，写了「文件落在 /xxx/uploads/ 下且可解析」才是有价值的结论。*

## 九、踩坑记录

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 访问上传后的文件 404 | 路径拼错，或访问的是相对路径 | 用页面上给出的完整路径拼成完整 URL 再访问 |
| 页面直接显示源码 | 该目录不解析这类后缀 | 说明执行条件不成立，这本身就是结论 |
| 提示语法错误 | 文件内容写错（少了分号、标签不闭合） | 先用最简单的单行内容验证，再逐步加 |
| 能执行但没有预期输出 | 相关函数被配置禁用 | 记录为「执行受限」，仍然说明文件被解析了 |

第三行提示了一个好习惯：上传的文件内容越短越好。验证「是否被解析」只需要一行输出，不需要任何复杂逻辑——这一步的目的只是确认条件，不是做别的事。

## 十、小结

- 上传点的根本问题不是「没查后缀」，而是「存储目录可执行」。

- 先传普通图片摸路径，再传最小内容验解析，两步就能定性。

- 校验要白名单化：允许什么，而不是禁止什么。

- 四层防护各有分工，执行层是最根本的那一层。

- 报告里必须写确切路径与解析结果，这是结论的可复现依据。

*下一篇把话题推进一层：当站点确实开始加各种检查，这些检查分别放在哪一层，哪些能挡住、哪些挡不住，以及为什么白名单是唯一难绕的一种。*
