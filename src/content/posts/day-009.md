> 拿到一个域名之后，能问出多少信息？注册人是谁、什么时候注册的、托管在哪家云、邮件服务器在哪、有哪些子域名还活着——这些问题全部可以只靠公开的 DNS 和 WHOIS 服务回答，一个包都不用往目标打。这篇把 whois、dig、子域名枚举三件事做成一条流水线，最后收成一张「五个维度」的资产画像。

## 一、信息收集的两个层次

上一篇文章讲的是用搜索引擎找「已经泄露在明面上的东西」。这一篇往下走一层——域名本身的注册信息和 DNS 记录。这部分数据是互联网基础设施的公共账本，任何人可查，目标完全无感知。

为什么值得花时间？因为一个域名背后通常不是一个站，而是一整个资产群。主站可能加固得很好，但三年前上线的测试子域、忘了下线的旧系统、直连数据库的 mail 服务器，这些才是真正的入口。

> **说明** 本文所有查询针对示例域名与自建测试环境，使用公开 WHOIS / DNS 服务，未对任何未授权目标发起探测。子域名枚举仅记录结果，不做访问验证。

## 二、WHOIS：查域名是谁的

WHOIS 是域名注册信息的公开查询协议。一条命令下去，返回的是这个域名的「户口本」。

*基础查询*

```text
whois example.com
```

输出很长，真正要抓的是四个字段：

| 字段 | 含义 | 信息价值 |
| --- | --- | --- |
| Registrar | 注册商 | 判断在哪家买的，间接推断使用习惯与预算 |
| Creation Date | 注册时间 | 越老越可能有历史遗留系统；新注册的站可能是临时资产 |
| Registrant | 注册人信息 | 现在基本被隐私保护屏蔽，能拿到就是意外收获 |
| Name Server | DNS 服务器 | 反推托管商。NS 指向某云厂商，说明整套基础设施在那家云上 |

![图 1　whois 查询结果的关键字段](/images/csdn/week02/Day009-1.png)

Name Server 这一栏是四个里最有用的。它不像注册人那样被脱敏，永远可见，而且直接暴露了 DNS 托管方——很多时候还能顺带看出这家公司同时用了哪几家云。

## 三、dig：把 DNS 记录一类一类问清楚

dig 是 DNS 查询的标准工具，比 nslookup 输出更规整、参数更灵活。核心用法是 dig 域名 记录类型。

### 3.1　A 记录：域名指向哪个 IP

*查 A 记录*

```text
dig example.com A +short
```

A 记录是最基础的——域名解析到哪个 IP。+short 参数让输出只留结果，去掉一堆头部信息，方便脚本处理。

拿到 IP 之后可以做两件事：一是反查（dig -x IP）看这个 IP 上还挂了哪些域名；二是判断这个 IP 属于哪家云（查 IP 归属），从而知道目标的基础设施在哪。

![图 2　查询 A 记录拿到目标 IP](/images/csdn/week02/Day009-2.png)

### 3.2　MX 记录：邮件服务器在哪

*查 MX 记录*

```text
dig example.com MX +short
```

MX 记录指向收邮件的那台服务器。它的价值在于：邮件网关通常是整个基础设施里最老、最难升级、暴露面最大的组件之一。如果 MX 指向的是自建服务器而不是第三方邮件服务（如腾讯企业邮、Google Workspace），那就说明有一台自己维护的邮件系统对着公网。

![图 3　查询 MX 记录找到邮件服务器](/images/csdn/week02/Day009-3.png)

### 3.3　NS 记录与 TXT 记录

*查 NS 与 TXT*

```text
dig example.com NS +short
dig example.com TXT +short
```

NS 记录在 WHOIS 里已经看过一次，这里用 dig 再确认一遍——两者有时不一致，不一致本身就是线索（可能刚迁过 DNS）。

TXT 记录容易被忽略，但经常藏着东西：SPF 记录会列出所有被授权发信的 IP 段，等于告诉你它有哪些邮件出口；域名验证记录会暴露它用了哪些第三方服务（Google、Microsoft、各类 SaaS）；有些公司甚至把内部备注写进 TXT。

### 3.4　反查与 ANY

*反向解析与全类型查询*

```text
dig -x 8.8.8.8 +short
dig example.com ANY +short
```

dig -x 是反向解析：给一个 IP，问它对应什么域名。在拿到一批 IP 之后，逐个反查能拼出「这台机器上还托管了谁的站」。ANY 查询理论上一次返回所有记录类型，但很多 DNS 服务器现在会拒绝或只返回部分，实际用途有限，知道有这个用法即可。

## 四、子域名枚举：把资产面铺开

主域名只有一个，子域名可能几十上百个。枚举子域名的意义在于——每一个子域都是一个独立的入口，而且往往比主站疏于管理。

### 4.1　dnsrecon 字典爆破

*dnsrecon 暴力枚举*

```text
dnsrecon -d example.com -t brt
```

-t brt 是 brute force 模式，拿内置字典逐个拼接成 xxx.example.com 去查询，能解析的就记下来。速度快、不需要任何权限、目标 DNS 服务器只会看到正常的解析请求。

![图 4　dnsrecon 暴力枚举出的子域名](/images/csdn/week02/Day009-4.png)

### 4.2　crt.sh：从证书透明日志里捞

证书透明（Certificate Transparency）是一项强制要求：所有公开 CA 签发的证书都必须登记到公开日志里。这意味着——任何一个申请过 HTTPS 证书的域名，都会在日志里留下永久记录，包括那些从没对外宣传过的内部子域。

*crt.sh 查询*

```bash
curl -s "https://crt.sh/?q=%25.example.com&output=json"
```

q=%25.example.com 里的 %25 是 URL 编码的百分号，等价于 SQL 里的 % 通配符，意思是「任意前缀 + .example.com」。output=json 让结果以 JSON 返回，方便解析。

![图 5　crt.sh 上查到的证书记录](/images/csdn/week02/Day009-5.png)

### 4.3　搜索引擎补一刀

*搜索引擎侧的子域检索*

```text
site:*.example.com
```

把上一篇的 site: 语法套上通配符，能捞出被收录的子域页面。三种方法结果互补——dnsrecon 靠字典猜，crt.sh 靠证书日志，搜索引擎靠爬虫，谁也不知道对方知道什么。

dnsrecon 用默认字典跑出了 www、mail、ftp、dev 几条。crt.sh 上查到的更多，还包括几个已经下线的老系统子域名——这类「僵尸子域名」最危险，主站早就修好了，子站还挂着旧版本，DNS 记录却一直没删。

## 五、完整实战：五维信息一次收全

挑一个公开站点，把 WHOIS、A、MX、NS、子域名五样一次性收全。

*五维收集*

```text
whois example.com
dig example.com A +short
dig example.com MX +short
dig example.com NS +short
```

重点不是「查到了什么」，而是「从这些记录能推断出什么」。比如 NS 指向某家云厂商，就说明整个基础设施在那家云上；MX 是自建邮件服务器，就说明有一台对外暴露的邮件网关。

![图 6　五个维度信息收集的完整命令输出](/images/csdn/week02/Day009-6.png)

![图 7　五个维度的信息汇总表](/images/csdn/week02/Day009-7.png)

收完之后能用一段话描述出目标：域名注册于哪一年、托管在哪家云、邮件走自建还是第三方、有哪些对外暴露的子域名。这段话就是后面所有工作的基础。

## 六、踩坑记录

| 现象 | 原因 | 解决办法 |
| --- | --- | --- |
| WHOIS 里 Registrant 全是 REDACTED | GDPR 与各注册商的隐私保护政策 | 放弃这个字段，转而看 NS 与 Creation Date |
| sublist3r: command not found | Kali 新版不再预装该工具 | 改用 dnsrecon + crt.sh，效果相当甚至更全 |
| dnsrecon 只跑出几条 | 内置字典太小 | 换大字典 -D 指定文件，或用 crt.sh 补 |
| crt.sh 打不开 / 返回超时 | 站点本身不稳定，查询量大时经常 502 | 重试、加超时参数，或换用同类证书日志查询站 |
| Windows 上没有 dig | dig 属于 BIND 工具包，Windows 默认没有 | 用 nslookup -type=MX 域名 替代，或装 WSL |

### 坑 1：WHOIS 查不到注册人

第一次跑 whois，看到 Registrant 那一栏是「REDACTED FOR PRIVACY」，一度以为工具坏了或者查错域名。

实际上这是现在的常态。GDPR 生效后，绝大多数注册商默认对个人注册信息做脱敏。指望 WHOIS 拿到姓名邮箱，已经基本不现实。

但脱敏只针对注册人字段。Registrar、Creation Date、Name Server 三栏永远可见，而这三栏的价值其实更高——注册商能看出使用习惯，注册时间能判断系统新旧，NS 能反推托管商。换个角度看，能拿到的比拿不到的更有用。

### 坑 2：sublist3r 装不上

按教程敲 sublist3r -d example.com，返回 command not found。Kali 新版本已经不再预装这个工具了。

没有强行去 pip 装。原因很简单：子域名枚举这件事，dnsrecon 的字典爆破 + crt.sh 的证书日志已经覆盖得很全，再装一个聚合工具收益有限，反而多一层依赖风险。直接改用这两个，结果一样甚至更好——crt.sh 能挖到 dnsrecon 字典里根本没有的域名，因为它不靠猜，靠真实签发记录。

### 坑 3：dnsrecon 结果太少

默认字典跑出来只有 4 条，感觉没挖到东西。

两个原因：一是内置字典确实小，二是很多子域用了泛解析或者根本没配 DNS 记录。改法是加 -D 指定更大的字典文件，同时用 crt.sh 交叉补。经验上，crt.sh 的结果通常是 dnsrecon 的 2–5 倍，因为证书日志记录的是「真实申请过证书的域名」，而字典爆破只能覆盖常见命名。

### 坑 4：crt.sh 时好时坏

crt.sh 经常返回 502 或者转很久。这是站点自身的问题，查询量大时它扛不住。

处理：重试几次，加 curl --max-time 30 限制超时；或者换用其他证书日志查询入口。这一类「公共查询服务」都不保证可用性，脚本里要写成失败可跳过的形式，不能卡死在一个源上。

### 坑 5：Windows 下没有 dig

在宿主机 Windows 上想验证一下结果，发现 dig 不存在。dig 是 BIND 工具包的一部分，Linux 自带，Windows 没有。

替代方案：nslookup -type=MX example.com，虽然输出格式啰嗦，但功能覆盖 A/MX/NS/TXT 全部类型。要完整的 dig 体验就装 WSL 或者用在线 DNS 查询工具。

## 七、小结

- WHOIS 抓四个字段：Registrar、Creation Date、Registrant、Name Server；注册人基本被脱敏，NS 才是真正的情报点。

- dig 按类型问：A 拿 IP、MX 找邮件网关、NS 反推托管商、TXT 挖第三方服务和 SPF 段、-x 反查同 IP 的其他域名。

- 子域名枚举三路互补：dnsrecon 靠字典猜、crt.sh 靠证书日志、搜索引擎靠爬虫，三者的交集最可信，并集最全。

- 僵尸子域名是重点：主站修好了但子站还挂着旧版本，这类资产通常无人维护，是最典型的突破口。

- 整套流程零流量打在目标上，全部通过公开基础设施完成——这就是被动信息收集的价值。
