> 上一篇解决了「为什么能注入」。这一篇看「注入之后能走到哪一步」，重点不在拿数据，而在于搞清楚每一步走得通的条件是什么——因为每一条条件，就是一个可以关掉的开关。全程在自建靶场内进行，只读观察，不做任何写操作。

## 一、一条注入的推进顺序

不管是手工还是工具，一条注入能看到多少东西，走的是同一条固定路径。每一步的产出都是下一步的输入，跳步必失败。把这条链画出来，防护点自然就浮现了。

| 阶段 | 需要突破的条件 | 对应的防护措施 |
| --- | --- | --- |
| 判断类型 | 引号是否被转义 / 参数是否被转成整数 | 参数化查询，或强制整型转换 |
| 数清列数 | 查询结果列数能否被外部推断 | 统一返回结构，错误信息不外露 |
| 找回显位 | 哪些列的内容会出现在响应里 | 敏感字段不直接渲染，做脱敏 |
| 读基础信息 | 数据库版本、库名、用户权限 | 最小权限账号，禁用高危函数 |
| 遍历元信息 | 能否读到 information_schema | 数据库账号按库授权，隔离业务库 |
| 取业务数据 | 目标表是否在这个账号的可读范围 | 分库分权限，敏感列加密存储 |

> **说明** 文中所有请求都发向本机 Docker 中运行的 DVWA 靶场（127.0.0.1），属代码审计与自查练习。真实系统上的同类验证必须在书面授权范围内进行，且只做只读判断。

## 二、第一步：判断参数类型

数字型和字符型的差别只在于原语句有没有给参数套引号。数字型可以直接接算术和逻辑表达式，字符型必须先闭合引号。方向判错的代价很大——后面所有尝试都会失败，而失败原因又看不出来。

*bash*

```text
1 AND 1=1
1' AND '1'='1
```

第一条报语法错误、第二条正常返回，说明这个点是字符型。判断依据只有「报不报错」这一个信号，所以哪怕错误信息被完全屏蔽，这个方法依然成立。

![图 1　字符型注入的确认（测试环境）](/images/csdn/week03/Day016-1.png)

### 1.1 从防护视角看这一步

这一步之所以能做完，前提是两条：响应在两种输入下表现不同、且差异可观察。防护的做法不是去藏差异，而是让输入根本走不到 SQL 解析——参数化查询之后，引号在参数里就是普通字符，语法结构不会因它改变。

## 三、第二步：推断结果集列数

ORDER BY 后面跟的是列序号，超出实际列数时数据库会拒绝解析。所以从 1 开始往上加，第一个被拒绝的数字减一，就是列数。

*bash*

```text
1' ORDER BY 1 --
1' ORDER BY 2 --
1' ORDER BY 3 --
```

1 和 2 都正常，加 3 时返回 Unknown column 错误，说明查询结果集是 2 列。

![图 2　列序号越界时的报错，边界由此确定](/images/csdn/week03/Day016-2.png)

### 3.1 为什么这个方法在屏蔽报错后仍有效

它依赖的不是报错内容，而是「正常 / 异常」这一个二元状态。只要两种状态还能被区分，推断就能继续。这也解释了一件事：**关闭错误回显只是提高了成本，不是防护**。真正的阻断点在参数化查询。

## 四、第三步：定位会显示到页面的字段

联合查询要求前后两个 SELECT 的列数完全一致，这正是必须先数清列数的原因。用数字占位之后，页面上哪个位置显示 1、哪个位置显示 2，那两个字段就是可被替换的位置。

*bash*

```text
1' UNION SELECT 1,2 --
```

页面在 First name 位置显示 1，Surname 位置显示 2，说明这两列会直接渲染到响应里。

![图 3　用占位数字定位可回显的字段](/images/csdn/week03/Day016-3.png)

> **防护重点** 这一步暴露的问题不是「注入存在」，而是「模板把查询结果原样渲染」。同一套查询逻辑里，只要需要展示的字段被显式列举、敏感列不进入返回结构，即便前两步失守，能泄露的范围也被压缩到很窄。

## 五、第四步：读取数据库基础信息

有回显位之后，把函数塞进 SELECT 就能直接读到结果。先看三样：版本、当前库名、当前用户。这三样决定了后续能力边界——版本决定语法特性，当前用户决定权限。

*bash*

```text
1' UNION SELECT version(),database() --
1' UNION SELECT user(),2 --
```

返回 5.7.x 的版本号、当前库 dvwa、当前用户 root@localhost。注意最后这一项：**应用使用 root 直连数据库**，这是实际项目里最该改的一条。

![图 4　版本、当前库与连接账号](/images/csdn/week03/Day016-4.png)

### 5.1 root 账号意味着什么

应用账号拥有 root 权限时，一条注入能触及的范围不止业务库：系统库、其他业务库、文件读写函数都在权限之内。把连接账号降级到「只对本业务库有 SELECT / INSERT / UPDATE」，同样一条注入能拿到的信息量会下降一个量级。这是投入产出比最高的一条整改。

## 六、第五步：遍历元信息库

MySQL 5.0 之后所有结构元数据都在 information_schema 里，tables 表存表名、columns 表存列名。这是自动化工具能一键出结果的根本原因：结构本身是可以被查询的。

*bash*

```text
1' UNION SELECT table_name,2 FROM information_schema.tables WHERE table_schema=database() --
```

列出 guestbook 和 users 两张表。把 table_schema 写成 database() 比写死库名更稳，换库不用改语句。

![图 5　从元信息库中列出表名](/images/csdn/week03/Day016-5.png)

## 七、第六步：取出业务字段

拿到表名后，同样从 columns 表查列名，再把真实列塞进联合查询。到此为止，如果账号权限足够，业务数据就已经在页面上了。

*bash*

```text
1' UNION SELECT column_name,2 FROM information_schema.columns WHERE table_name='users' --
1' UNION SELECT user,password FROM users --
```

用户表共 8 列，关键的是 user 和 password。取出的口令字段是 32 位十六进制摘要，不是明文——这一层是靶场刻意保留的最后一个缓冲。

![图 6　取出的账号与口令摘要](/images/csdn/week03/Day016-6.png)

### 7.1 口令摘要不是终点

摘要不可逆，但对弱口令来说，摘要本身是查表可得的。靶场里那条最常见的口令，在公开的摘要表里一查就出来。这说明一件事：**口令强度决定了摘要泄露之后的实际风险**。整改顺序上，口令复杂度策略和账号锁定策略的价值，不亚于堵住注入本身。

## 八、把这条链变成自查清单

上面六个阶段，每个都有一个可以立刻检查的点。按投入产出比排序：

| 优先级 | 检查项 | 判定标准 | 整改动作 |
| --- | --- | --- | --- |
| P0 | 是否存在字符串拼接 SQL | 全局搜索 SQL 拼接，看变量是否进入引号内 | 改参数化查询，占位符绑定 |
| P0 | 数据库连接账号权限 | 账号是否为 root / 是否有 FILE、DROP 权限 | 按库按表最小授权，业务账号禁 DDL |
| P1 | 错误信息是否外露 | 构造语法错误的输入，看响应是否含数据库原文 | 统一异常页，关闭 display_errors |
| P1 | 响应中的字段结构 | 返回体是否原样渲染查询结果、是否含无关列 | 显式列举字段，敏感列脱敏 |
| P1 | 口令存储方式 | 是否 MD5 / SHA1 单轮摘要 | 换 bcrypt / Argon2 等慢哈希加盐 |
| P2 | 元信息库可读性 | 业务账号能否读 information_schema 全量 | 按库隔离，跨库查询走受控接口 |

## 九、踩坑记录

| 坑点 | 症状 | 解决办法 |
| --- | --- | --- |
| 联合查询报错 | Column count doesn't match | 列数不对，回上一步重新确认 |
| 列序号一直不报错 | 加到 10 仍然正常 | 原语句没被注释，尾部干扰了解析 |
| 查不到表名 | 返回空结果 | 库名条件写错，改用 database() 避免拼错 |
| 回显位是空的 | 联合查询成功但页面没数字 | 该列不渲染，换其他位置再试 |
| 摘要查不出来 | 公开摘要表里没有 | 不是所有摘要都在表里，属正常现象 |

几条补充说明：

- **列数不对**最容易被忽略的细节是：报错说的是「前后列数不一致」，但真正原因可能是原语句尾部没被注释，多了一截。先确认注释生效，再怀疑列数。

- **查不到表名**多半是条件写错。用 database() 而不是写死库名，能避免一类拼写错误。

- **回显位为空**说明那一列不参与模板渲染。这时候不要放弃，换个位置继续试——这条经验反过来就是防护建议：不渲染的字段等于少一条泄露通道。

- **摘要查不出来**是正常现象。用这一点反推：只要口令本身够强，摘要泄露不等于账号沦陷。

## 十、小结

- 注入的推进路径是**固定且可预测**的，所以防护点也是可枚举的——把每一阶段的条件掐断，链条就断在那一环。

- 投入产出比最高的两条：**参数化查询**（断根）和**数据库账号降权**（限制影响半径）。其余都是纵深。

- 关闭错误回显不是防护，只是提高了成本。把它当成纵深的一层，别当终点。

- 口令摘要不是「泄露即失守」，但弱口令让这一层缓冲形同虚设。口令策略要与注入防护同等级对待。
