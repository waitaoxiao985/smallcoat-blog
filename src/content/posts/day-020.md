> 前面四篇各讲一个侧面：原理、推理链、自动化工具、盲通道、过滤失效。这篇把它们串起来，在同一个靶场的四个防护级别上走一遍，重点不是「能不能打进去」，而是**同一种判断在不同防护下要换什么观察方式，以及验证记录该写到什么颗粒度**。

## 一、为什么要跨防护级别做同一件事

单点验证容易得出片面结论：在低防护下成功，会误以为这个点「一直存在」；在高防护下失败，会误以为这个点「已经修好」。实际情况是防护级别不同，暴露的入口也不同。逐级过一遍，才能说清「哪一层在起作用」。

| 场景 | 防护重点 | 需要的验证方式 | 主要观察量 |
| --- | --- | --- | --- |
| Low | 几乎没有防护 | 直接传参即可 | 页面回显 |
| Medium | 字符串转义 + 前端限制 | 构造请求体，走数字型入口 | 响应条数 |
| High | 区域限制 + 语句收尾 | 注意语句尾部处理 | 响应条数 |
| 独立靶场 | 分关卡教学 | 按关卡逐个走标准流程 | 页面回显 / 状态 |

> **说明** 全部操作在本机 Docker 中运行的开源靶场（DVWA 与 SQLi-Labs）完成，属代码审计与自查练习。真实系统上的同类验证需有书面授权，且只做只读判断，不修改、不删除任何数据。

## 二、场景一：低防护下的完整链路

低防护级别的入口是字符型，标准五步就能走通：判类型 → 数列数 → 找回显位 → 取库表 → 取数据。这一步的目的是建立基准——后面三个场景都要拿它做对照。

*bash*

```text
1' ORDER BY 2 --
1' UNION SELECT user,password FROM users --
```

回显直接给出账号与口令摘要，一次请求拿到全部记录。后续场景里，同样的目标需要换更长的路径才能达到同样的信息量。

## 三、场景二：转义生效之后改走数字型

防护级别调高，字符型入口的单引号被转义，前面那套写法全部失效。这时应该去看参数最终怎么被使用——如果它被当成数字，字符串层的转义根本不参与。

前端把输入做成了下拉框，但请求体可以任意构造，直接把参数改成表达式：

*bash*

```text
id=1  →  id=1 OR 1=1
id=1 ORDER BY 2
id=1 UNION SELECT user,password FROM users
```

数字型不需要引号闭合，转义函数对这段输入完全无作用。三条请求依次完成了「确认条件生效 → 确认列数 → 取数据」。

![图 2　构造请求体走数字型入口](/images/csdn/week03/Day020-2.png)

> **这一步的教训** 我在这个场景上卡了半小时，一直按字符型去试。停下来读一遍后端源码，比继续试三十次有用得多。**先确认参数的用法，再决定用哪套写法**，是这一周最省钱的一条经验。

## 四、场景三：语句尾部被固定时怎么处理

更高防护级别下，后端把语句末尾固定加了一段限定，取回的永远只有一条记录，看起来像「没有漏洞」。但固定的那部分只是语句的一部分——能被注释掉，前面的构造就重新生效。

*bash*

```text
1' OR '1'='1' #
1' UNION SELECT user,password FROM users #
```

行内注释符把后面的限定截断，返回结果从一条恢复成全部。这个场景说明一件事：**「结果被限制」不等于「注入不成立」**，判断要看行为差异，不能看条数多少。

## 五、场景四：换一个独立靶场复现同一套流程

在单一靶场练熟容易形成路径依赖，换一套环境才能检验方法是不是真的掌握了。用容器起一个分关卡的开源靶场，按难度递进逐关走：

*bash*

```bash
docker run -d -p 8080:80 acgpiano/sqli-labs
```

前两关与前面场景同源，很快通过；第五关开始不再回显，属于盲通道，正好接上前面写过的二分法；第十一关换成表单提交，参数位置变化但方法不变。整轮走完的路径是固定的五步：

- **检测**：拿一个真条件和一个假条件撞，看响应是否可区分。

- **判断类型**：字符型还是数字型，决定要不要闭合引号。

- **确定结构**：列数、回显位，为取数据铺路。

- **提取数据**：先库、再表、再列、最后记录，一级一级收窄。

- **遇到阻断时记录原因**：防护、编码、还是自身写法有误，分清再决定下一步。

盲关卡的自动化脚本用的是最朴素的双重循环 + 二分：把字符转成 ASCII 码，每次把区间砍半，判据就是页面里那句固定的「命中」文字。写下来不到三十行，但它是前面五篇所有道理落到代码的样子。

*python*

```text
def q(payload):
    r = requests.get(URL, params={"id": payload}, timeout=8)
    return "You are in" in r.text

def get_str(pos):
    lo, hi = 32, 126
    while lo < hi:
        mid = (lo + hi) // 2
        if q(f"1' AND ASCII(SUBSTRING(database(),{pos},1))>{mid} -- "):
            lo = mid + 1
        else:
            hi = mid
    return chr(lo)
```

## 六、验证记录该写到什么颗粒度

这一周的最后一个收获是记录规范。同一个发现，写「存在 SQL 注入」和写清「哪个参数、什么防护级别、用什么请求、响应差在哪、能取到多少信息」，价值完全不同。后者才是别人能照着复现的东西。

| 记录项 | 写什么 | 为什么要写 |
| --- | --- | --- |
| 位置 | 接口路径 + 参数名 + 请求方式 | 决定别人能否定位到同一处 |
| 前置条件 | 防护级别、登录状态、依赖的会话 | 不写清就无法复现 |
| 判断依据 | 真条件与假条件的响应差异 | 这是「成立」的唯一证据 |
| 影响范围 | 能读到哪些库表、到什么程度 | 决定定级，避免夸大 |
| 阻断情况 | 受阻在哪一层、表现是什么 | 说明防护起作用的部分 |

> **只读原则** 整个过程中所有请求只做查询读取，没有写入、修改、删除任何记录，也没有在目标上留下文件。验证的目的是证明「能读到不该读到的数据」，做到这一步就足够说明问题，继续往下做只会增加风险而不增加信息量。

## 七、踩坑记录

| 坑点 | 症状 | 解决办法 |
| --- | --- | --- |
| 按字符型死磕数字型入口 | 怎么加引号都不通 | 先读后端用法，再选写法 |
| 结果只有一条就判定无漏洞 | 以为被拦住了 | 去掉语句尾部的限定再看 |
| 靶场镜像拉不下来 | 容器一直起不来 | 换用预置镜像源或本地已有镜像 |
| 换靶场后路径依赖 | 新环境无从下手 | 回到五步流程，从检测重新开始 |
| 脚本判据写错 | 二分永远不收敛 | 拿已知结果回测一次判据 |

## 八、小结

- **同一种判断在不同防护级别下要换观察方式**：回显没了看条数，条数没了看时间。

- 数字型入口是转义防护的天然缺口——先确认参数用法，比多试三十次有效。

- 结果被限制不代表注入不成立，判断要看行为差异。

- 记录颗粒度决定了这次验证有没有价值：位置、条件、依据、影响、阻断，五项缺一不可。

- 全程只读，做到「能读到不该读到的数据」就停手——再往下只增风险不增信息。
