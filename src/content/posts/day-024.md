> 前两篇我们确认了「输入被当成代码」这个事实。今天换一个视角：假设站点已经加了过滤，这个过滤到底是怎么判断的？判断依据放在哪一层，决定了它拦得住什么、拦不住什么。本篇不复述具体绕过写法，而是把六种常见过滤方式逐个拆开，看每种方式为什么只能拦住一部分，以及真正拦得住的那一类为什么难绕。

## 一、先看过滤在不在，再问它判断什么

该靶场的 XSS 模块把安全级别从 Low 调到 Medium，同一个输入框，行为就变了。这时候不要急着换写法，先做一件事：把一段最普通的标签输进去，看它被怎么处理。

*第一种探测动作*

```text
输入：<script>alert(1)</script>

可能看到三种结果：
1. 整段消失，页面什么都不显示 —— 输入被删除了
2. 只剩下 alert(1) —— 标签被替换成了空字符串
3. 页面原样显示这段文字，但不弹窗 —— 被实体编码了
```

这三种结果指向三种完全不同的防护机制。第一种是删除式黑名单，第二种是替换式黑名单，第三种是输出编码。前面两种还能继续想办法，第三种说明防护方向是对的——它把内容变成了纯文本，标签永远不会被解析。

> **判断顺序很重要** 先分清「过滤」和「编码」，再谈绕过。过滤是在猜坏人长什么样，编码是让数据永远只是数据。前者总有机会，后者基本没有。

## 二、六种过滤方式，逐个看它的判断依据

把常见的防护做法列成一张表，右侧写明它凭什么做判断——这一列才是关键。

| 防护方式 | 判断依据 | 拦得住什么 | 为什么会有缺口 |
| --- | --- | --- | --- |
| 前端脚本校验 | 浏览器里那段 JS 的逻辑 | 正常浏览器的正常提交 | 请求可以不经浏览器直接发出，服务端仍要处理 |
| 请求头里的类型字段 | 客户端自己声明的类型 | 声明得诚实的请求 | 这个字段由客户端提供，可以改 |
| 文件后缀黑名单 | 文件名结尾的几个字符 | 列在黑名单里的后缀 | 不在名单里的写法永远存在 |
| 文件后缀白名单 | 只允许列出的后缀 | 绝大多数可执行后缀 | 需要配合解析配置漏洞才有缺口，本身很硬 |
| 内容开头字节 | 文件头几个字节 | 纯文本形式的内容 | 在前面加一段合法头就能骗过 |
| 内容特征匹配 | 内容里是否含某些字符串 | 写死的那些特征串 | 拆分、变形、编码后特征就变了 |

这张表的第二列是我今天最大的收获。所有黑名单类判断的依据都是「已知的坏东西长什么样」，而已知永远是有限的；白名单类判断的依据是「只允许已知的好东西」，未知的东西进不来。这一句话解释了为什么白名单难绕、黑名单永远绕得过去。

## 三、大小写与重复：两个最朴素的缺口

第一个缺口来自字符串比较。如果过滤逻辑是「内容里出现指定字符串就拦」，那么换个大小写就能通过——因为字符串比较是区分大小写的，而浏览器解析标签是不区分大小写的。

*缺口一：大小写*

```text
过滤规则（示意）：内容含 script 就拒绝

被拦住的：<script>alert(1)</script>
能通过的：<ScRiPt>alert(1)</ScRiPt>
```

第二个缺口来自「只替换一次」。如果过滤逻辑是把命中的字符串替换成空，且只做一次替换，那么把关键字拆开写，拼装后仍然会形成完整的关键字。

*缺口二：只替换一次*

```text
过滤规则（示意）：把 script 替换为空，只替换一次

输入：<scr<script>ipt>alert(1)</scr</script>ipt>
第一次替换后剩下的部分，恰好又拼回了完整的标签
```

这两个缺口有个共同点：过滤逻辑假设「坏东西只有一种写法」，而解析器对同一个语义接受多种写法。过滤器和解析器用的不是同一套规则，缺口就出现在规则差异里。

## 四、换一个入口：不是所有执行都需要 script

还有一类缺口更根本：过滤只盯着 script 这一个标签，但浏览器里能触发脚本的位置远不止这一个。图片加载失败、元素加载完成、媒体元素的事件属性，都能执行脚本。

| 触发位置 | 触发时机 |
| --- | --- |
| 图片元素的错误事件 | 图片地址无效、加载失败时触发 |
| 矢量图元素的加载事件 | 元素被解析进页面时触发 |
| 页面主体元素的加载事件 | 页面主体渲染完成时触发 |
| 媒体元素的事件 | 播放、出错等状态变化时触发 |
| 动画元素的事件 | 动画开始、结束时触发 |

这张表说明的问题是：只拦标签名，等于只堵了一个门。真正要拦的不是某个标签，而是「数据被当成代码执行」这个动作本身——也就是编码和 CSP 做的事。

## 五、会话凭证的两种存法，决定了利用链能走多远

前面几节都在讲「怎么让脚本跑起来」。这一节讲「跑起来之后能拿到什么」，而这一半完全由服务端的配置决定。

如果会话凭证以脚本可读的方式存放，那么页面里任意脚本都能读走它；如果这个 Cookie 带了 HttpOnly 标记，脚本读不到，只能看到一串空值。第三种情况是把这个标记加上 CSP，脚本连执行的机会都没有。

| 服务端配置 | 脚本能做什么 | 利用链是否成立 |
| --- | --- | --- |
| Cookie 无 HttpOnly、无 CSP | 读取凭证、冒充请求、篡改页面 | 完整 |
| Cookie 有 HttpOnly、无 CSP | 不能读凭证，但仍能冒充请求、篡改页面 | 部分 |
| 有 HttpOnly 且有 CSP | 脚本难以执行 | 基本不成立 |

> **这条结论值得记住** 前端过滤决定「能不能执行」，服务端配置决定「执行了能拿走什么」。只看前者，会把一个部分风险误判成完整风险；只看后者，会低估一个没有 HttpOnly 的站点的实际暴露面。

## 六、真实场景里这条链长什么样

这一节只讲场景结构，不讲操作细节。四种典型场景，差别在「诱导方式」和「凭证流向」。

| 场景 | 诱导方式 | 拿到的是什么 |
| --- | --- | --- |
| 会话凭证被读取 | 诱导点击一条构造好的链接 | 以受害者身份继续操作的能力 |
| 键盘输入被记录 | 页面被注入监听逻辑 | 用户在该页面上输入的所有内容 |
| 登录表单被伪装 | 页面被替换成仿冒表单 | 用户主动交出的账号与密码 |
| 内容自动扩散 | 被注入的内容自我复制到其他用户可见的位置 | 影响范围指数级扩大 |

第四行是需要单独提的：当「用户可写、别人会看」的字段被串联起来，一条内容可以自己往外扩散，不需要任何人工投递。这也是为什么昵称、签名这类看似无害的字段，一旦出问题影响面会特别大。

## 七、把防护按成本排序

既然黑名单永远有缺口，防护该怎么排优先级？我的排序如下，从必做到加分。

- 第一层，输出编码：所有把用户输入写回页面的位置，按上下文（HTML 正文、属性、脚本、URL）分别编码。这是必做项，也是唯一能覆盖所有类型的一项。

- 第二层，会话 Cookie 加 HttpOnly 与 Secure：即使脚本执行了，也拿不走凭证。改动小、收益直接。

- 第三层，响应头加 CSP：限制脚本来源，禁掉内联脚本。改造量最大，但拦住的是执行本身。

- 第四层，富文本走白名单清洗：确实要允许部分标签时，用成熟的清洗库按白名单放行，不要自己写替换规则。

- 第五层，前端校验只作为体验优化：能省一次往返，但不能当成安全措施。

*一句总结：过滤是「猜坏人长什么样」，编码是「让数据永远只是数据」。前者是黑名单思路，后者才是白名单思路。*

## 八、自查清单

- 把站点里所有「用户输入写回页面」的位置列出来，逐个确认编码是否与上下文匹配。

- 检查会话 Cookie 是否带 HttpOnly、Secure，检查响应头是否配了 CSP。

- 所有同意用户上传文件的入口，确认校验是在服务端完成的，且校验的是「允许什么」而不是「禁止什么」。

- 前端代码里搜 innerHTML、document.write、eval、location.href 这几处，确认拼进去的内容是否可信。

- 把上面四项做成上线前的检查表，新功能照表过一遍。

## 九、踩坑记录

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 改大小写没效果 | 过滤用的是不区分大小写的匹配 | 说明这一层防得比想象中严，换方向看其他入口 |
| 拆分写法拼不出完整标签 | 替换做了多轮，或匹配方式不同 | 不要死磕一种写法，去看过滤逻辑到底判断什么 |
| 页面里注入的内容发不出去 | 响应头里有 CSP | 这说明防护上了一层，记录并转向别的验证点 |
| 验证脚本拿不到值 | Cookie 带了 HttpOnly | 记录为「不可读凭证」，本身就是一个有价值的防护确认 |

最后一行值得单独说：验证失败不等于没有收获。「这里有 HttpOnly」和「这里有 CSP」本身就是结论，它告诉客户哪一层防护是有效的，剩下的风险面在哪里。

## 十、小结

- 绕过技巧的多少，反映的是防护思路的强弱，不是利用者的水平。

- 所有黑名单的判断依据都是「已知的坏东西」，未知的写法永远存在。

- 编码解决「会不会被执行」，Cookie 标记与 CSP 解决「执行了能拿走什么」，两者缺一不可。

- 验收标准要从「能不能弹窗」升级成「能不能带走东西」，前者只是漏洞存在，后者才是真实影响。
