> 上一篇确认了「上传目录可执行」是根本原因。今天要回答的是另一半：当站点开始加校验，这些校验分别靠什么做判断？我在本地靶场上把安全级别从 Low 调到 Medium，把常见的六种校验思路逐个梳理了一遍。结论和上一篇一脉相承——凡是在猜「坏的东西长什么样」，就有缺口；凡是在明确「只要好的那一种」，就难补。

## 一、先看站点拦在了哪一步

把校验实践的第一步不是换写法，而是看反馈。上传一个明显不合规的文件，观察站点给出的提示——提示内容本身就暴露了它在检查什么。

*从提示反推校验位置*

```text
提示「文件类型不被允许」      → 在检查类型声明
提示「后缀不被允许」          → 在检查文件名结尾
提示「文件内容不符合要求」    → 在检查内容特征
提示「文件过大」              → 在检查大小
没有任何提示，直接上传失败    → 检查发生在更前面（如前端脚本）
```

该靶场的 Medium 级别通常是两层：后缀 + 类型声明。判断出这两层之后，接下来的问题就变成「这两层的判断依据分别可靠吗」。

## 二、六种校验思路对照

这张表是今天的主干。第二列写的是「它凭什么做判断」，第三列是「为什么这个依据靠不住」。

| 校验方式 | 判断依据 | 为什么会有缺口 |
| --- | --- | --- |
| 前端脚本校验 | 浏览器里执行的 JS | 请求可以不经浏览器直接发出，服务端仍要独立校验 |
| 类型声明字段 | 客户端自己声明的 Content-Type | 字段由客户端填写，可以任意修改 |
| 后缀黑名单 | 文件名结尾是否命中已知列表 | 同一语义的多种写法永远列不全 |
| 后缀白名单 | 文件名结尾是否在允许列表内 | 本身很硬，缺口只来自解析配置 |
| 内容开头字节 | 文件头几个字节是否匹配 | 在合法开头之后追加内容即可 |
| 内容特征匹配 | 内容里是否含某些字符串 | 拆分、变形、编码后特征即失效 |

> **这张表的读法** 前五种都在回答「这个文件是不是可疑」，靠的是对已知威胁的描述；只有第六种反过来回答「这个文件是不是我允许的那一种」，靠的是对自身需求的定义。前者永远在追赶，后者只需一次定义清楚。

## 三、客户端声明的类型为什么不能信

HTTP 请求里的类型字段，是客户端在发送时自己填的。它表达的是「我认为我发的是什么」，而不是「我实际发的是什么」。服务端如果直接采信这个字段，等于让被告自己写判决书。

*声明与实际是两件事*

```text
浏览器正常上传图片时发送的声明（示意）：
 Content-Type: image/jpeg

同一次上传，请求内容稍作调整后的声明（示意）：
 Content-Type: image/jpeg   ← 声明照旧，但实际内容不是图片
```

正确的做法是在服务端读取文件内容本身，判断它的真实类型（比如读取文件头几个字节对照格式表），并且只对允许的少数格式放行。注意「读取内容判断类型」和「读取内容匹配特征」是两件事：前者是白名单式判定，后者仍然是黑名单式匹配。

## 四、文件名这一层为什么复杂

文件名看起来简单，实际上是校验最容易出错的地方，因为「文件名」这个概念在不同系统、不同环节下的解释并不一致。下面几种情形都源于这个不一致——再次强调，列出它们是为了说明某类校验为什么不可靠，而不是给出操作步骤。

| 情形 | 为什么校验会失效 |
| --- | --- |
| 大小写混写 | 后缀比对区分大小写，但解析器不区分 |
| 多重后缀 | 不同环节取的是不同位置的后缀 |
| 尾随符号 | 操作系统会忽略某些尾随字符，校验逻辑不会 |
| 等效后缀 | 同一执行语义对应多个后缀名，名单难以穷举 |
| 编码变形 | 校验看到的是编码前，存储用的是编码后 |

这些情形有一个共同根源：校验逻辑与解析逻辑对同一个字符串的解释不一致。只要两者不一致，就存在「校验认为是 A、执行时当成 B」的空间。

> **正确的做法** 不要让用户决定文件名。服务端收到文件后，自己生成一个随机名，后缀由服务端按业务类型指定，原始文件名只写进数据库用于展示。这一条能一次性消掉上面整张表。

## 五、内容层校验的两个方向

内容层的校验有两种方向，效果差别很大。

| 方向 | 做法 | 评价 |
| --- | --- | --- |
| 匹配特征（黑名单） | 检查内容里是否出现某些已知特征串 | 永远有缺口，写法一变就失效 |
| 识别类型（白名单） | 按格式规范解析内容，确认它确实是声明的那种格式 | 推荐，未知格式直接拒绝 |

第二种做法的关键是「真正去解析」，而不是「看开头几个字节对不对」。真正解析意味着：图片要能被图像库正常打开并转码、文档要符合格式规范，解析失败即拒绝。把图片重新编码一次（俗称「重绘」）是最彻底的一种，因为它顺手把所有附加在文件里的其他内容都丢掉了。

## 六、把六种校验按有效性排序

如果让我给一个站点排上传防护的优先级，顺序是这样：

- 第一，存储目录不可执行。这一条与校验无关，却比任何校验都有效——传进来也跑不起来。

- 第二，服务端重命名 + 服务端指定后缀。切断「按名字访问」的路径，也消除了文件名层的所有花样。

- 第三，内容层白名单识别（真正解析后转码）。确保进来的确实是自己允许的那几种格式。

- 第四，类型声明与后缀白名单作为辅助。它们可以挡住大部分随手尝试，但不作为唯一依靠。

- 第五，前端校验只作为体验优化。它减少了无效请求，但不承担安全职责。

*一句话：能靠「不允许执行」解决的，不要靠「检查后缀」解决。后者是判断题，前者是物理隔离。*

## 七、真实场景里上传点的几种形态

做资产梳理时，上传点往往不止「选择文件」按钮这一个入口。下面这些位置同样是上传，容易被漏掉。

| 形态 | 为什么容易被漏 |
| --- | --- |
| 编辑器里的插入图片 | 走的是编辑器自带接口，与主站上传逻辑不同 |
| 导入功能（Excel / CSV / 压缩包） | 被认为是「数据导入」而非「文件上传」 |
| 头像裁剪 | 前端裁剪后仍会把图片上传到服务端 |
| 附件与工单 | 权限模型不同，常绕过主站校验 |
| 接口形式的直传 | 没有页面入口，只有 API，扫描器扫不到 |

第五行是重点：很多站点的上传接口是给移动端或前端直传用的，页面上看不到入口，但接口照样接受请求。梳理上传面时，接口清单和页面清单要一起看。

## 八、自查清单

- 把六种校验方式对照一遍，看自己的站点实际用了哪几种、缺哪一种。

- 确认上传目录是否禁止脚本解析——这是最应该先做的一件事。

- 确认服务端是否强制重命名、后缀是否由服务端指定。

- 确认内容层是否做了真正的解析与转码，而不只是看开头字节。

- 把所有接口形式的上传入口也纳入清单，不要只看页面上有按钮的位置。

## 九、踩坑记录

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 改了声明还是被拒 | 站点同时检查了后缀 | 说明是多层校验，先判断清楚拦在哪一层再继续 |
| 提示信息完全一样 | 站点统一了错误提示 | 从「是否被接收」这个结果本身判断，不依赖文案 |
| 上传成功但访问不到 | 文件名被重命名了 | 说明名称层防护有效，记录为「已重命名」 |
| 上传成功但显示源码 | 目录不解析脚本 | 说明执行层防护有效，这本身是重要结论 |

最后两行提醒一件事：在攻防演练或日常自查中，「被拦住了」往往比「进去了」更有价值——它告诉你哪一层是有效的，剩下的注意力就可以放到真正薄弱的地方。

## 十、小结

- 六种校验里，前五种都在猜「坏东西长什么样」，只有白名单在明确「我要什么」。

- 声明字段、文件名、开头字节这三层都存在「校验逻辑与解析逻辑不一致」的空间。

- 内容层唯一可靠的做法是真正解析并转码，而不是匹配特征。

- 最有效的一层与校验无关：让存储目录不可执行。

- 上传点不止页面上的按钮，接口形式的直传同样要纳入清单。

*下一篇换个角度：假设文件确实落到了服务器上，并且能被访问，接下来会面临什么？我们不写任何实际操作，只讲「一个可执行的文件意味着什么」以及「事后能留下哪些痕迹」。*
