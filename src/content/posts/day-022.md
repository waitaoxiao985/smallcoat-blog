> 上一篇结束时我们说，注入是「拼接」造成的。这一篇换一个方向：注入发生在数据库那一端，而 XSS 发生在浏览器这一端——服务器并没有拼错任何 SQL，它只是把用户输入原样放进了 HTML，然后浏览器替它执行了。本文在本地搭建的靶场上复现过程，目的不是学会弹窗，而是看清「输入被当成代码」这个判断标准，以及防护该落在哪一层。

## 一、先把实验环境说清楚

所有操作都在本机虚拟机里完成，靶场是 本地靶场，只在自己控制的地址上做，只验证到「弹出标记」这一步，不涉及任何真实站点。

| 项目 | 内容 |
| --- | --- |
| 靶场 | 本地搭建的测试靶场 |
| 访问地址 | http://[靶场地址]:8082 |
| 测试模块 | XSS (Reflected) |
| 安全级别 | Low |
| 本次目标 | 让页面执行一段自己写的脚本，并确认它出现在哪里 |
| 边界 | 仅本机靶场，仅验证执行，不做数据外带 |

*一句话原则：能在自己机器上复现的事，不要拿别人的站点当练习场。*

## 二、先看现象：一个正常的输入去了哪里

进模块后不要急着上脚本。先输入一个毫无利用性的词，比如 hello，看它出现在页面的什么位置、被包在什么标签里。这一步决定后面所有判断。

*第一次正常输入*

```text
在输入框输入：
hello

页面回显（示意）：
Hello hello
```

看到的结果是：我输入的内容被原封不动塞进了页面的 HTML 里，前面还拼了一个 Hello 前缀。这句话是整个 XSS 的起点——服务器对这段输入没有任何处理，它把「数据」放进了「代码的位置」。

接着换成一段脚本：

*把输入换成一个标签*

```text
<script>alert(1)</script>
```

页面弹出一个写着 1 的对话框。没有报错，没有拦截，浏览器老老实实地把这段文字当成可执行代码跑了一遍。

> **这里的关键判断** 弹窗本身没有意义，它只是一个信号。真正有意义的是这句话：浏览器愿意把我写的内容当成代码执行。既然任意脚本都能跑，那这段脚本能做的事，就等于我在这个页面上能做的事。

## 三、为什么这一步比弹窗严重：从执行到会话

把弹窗里的内容从 1 换成一个读取 Cookie 的表达式：

*读取当前页面的 Cookie*

```text
<script>alert(document.cookie)</script>
```

弹窗里出现的是一串 Cookie 内容。在 该靶场的默认配置下，登录状态就是靠 Cookie 里的会话标识维持的：服务器不认识「我」这个人，它只认识 Cookie 里那个字符串。也就是说，谁能拿到这个字符串，谁就能在不知道密码的情况下，以我的身份继续操作。

这就是 XSS 常被称作「会话劫持入口」的原因。利用链其实只有两步：第一步让页面执行脚本，第二步让脚本把凭证交出去。第一步我们刚刚验证完了，第二步在真实的利用里通常由一段外发请求完成。

> **为什么这条链在 该靶场里看起来轻飘飘** 因为这里 Cookie 没有开 HttpOnly，也没有 CSP 限制。真实站点如果开了 HttpOnly，脚本读不到 Cookie，第二步就断了——这也正说明防护点在哪一层：不在输入过滤，在凭证的可读性与脚本的可执行性。

## 四、反射型的三个判定特征

同样的弹窗，出现在不同位置，处理方式和危害完全不同。反射型 XSS 有三条很硬的判定特征，记住这三条就不会和别的类型混淆。

第一条：输入被原样输出到 HTML 里。刚才的 hello 已经证明了这一点。

第二条：脚本内容出现在 URL 里。把输入框里的内容提交之后，看地址栏：

*地址栏里的参数*

```text
正常访问：
http://[靶场地址]:8082/vulnerabilities/xss_r/?name=hello

提交脚本后：
http://[靶场地址]:8082/vulnerabilities/xss_r/?name=<script>alert(1)</script>
```

脚本被放在 name 这个查询参数里，服务器拿到参数后直接吐回页面。参数在 URL 上，就意味着这条 URL 本身可以被复制、被转发、被缩短。

第三条：刷新后不再触发。直接刷新页面，弹窗不会再现——因为参数被重新提交时已经变了，或者说这一次请求的生命周期结束了。这条特征把它和存储型彻底分开：存储型的内容已经进了数据库，谁来访问都会触发。

| 类型 | 脚本位置 | 持久性 | 危害面 |
| --- | --- | --- | --- |
| 反射型 | URL 参数 | 一次性 | 中 |
| 存储型 | 数据库 | 持久 | 高 |
| DOM 型 | 前端脚本读取的 URL 或属性 | 一次性 | 中 |

三种类型的分界线不在脚本长什么样，而在脚本「存在哪里、活多久」。这是我自己反复搞混过的地方：一开始总以为短的就是反射、长的就是存储，完全不是。

## 五、把类型放一边，先看危害的完整清单

弹窗只是证明漏洞存在。真正该记住的是：一旦浏览器愿意执行我写的脚本，我能做的事就是这张表。

| 能力 | 说明 |
| --- | --- |
| 读取页面数据 | Cookie、localStorage、页面里的表单值，凡是脚本能访问的都能读 |
| 篡改页面 | 改文案、改按钮、改跳转链接，用户看到的是「真站点里的假内容」 |
| 监听输入 | 绑定键盘事件，用户在这个页面上敲的每个字都能被记录 |
| 冒充请求 | 带着用户的会话，在后台发起他自己的操作（改密码、加好友、转账） |
| 引导下载 | 弹出下载或跳转到伪装页面，把风险从浏览器推到终端 |

这张表里，只有第一行和「拿到凭证」直接相关，其余几行即使 Cookie 开了 HttpOnly 也依然成立——脚本能在页面里跑，就能借用户的身份操作页面。所以我后来不再用「能不能弹出 Cookie」当作唯一的验收标准。

## 六、防护到底该落在哪一层

该靶场的 Low 级别之所以一打就中，是因为它什么都没做。往上调级别，能直接看到防护是一层层加上去的，而每一层的效果差别很大。

| 防护做法 | 拦得住什么 | 为什么还不够 |
| --- | --- | --- |
| 前端 JS 校验 | 拦掉正常浏览器的普通提交 | 请求可以绕过页面直接发，服务端仍然要处理 |
| 黑名单过滤标签 | 拦掉写死的那几种写法 | 标签和事件组合太多，永远有落网的写法 |
| HTML 实体编码输出 | 让标签变成纯文本、无法被解析 | 这是根本手段，但要选对上下文（HTML/属性/JS/URL 各不相同） |
| HttpOnly 标记 | 脚本读不到会话 Cookie | 只断掉窃取凭证这一条，改页面、冒充请求仍然成立 |
| CSP 内容安全策略 | 限制脚本来源与内联脚本 | 配置复杂，历史遗留页面改造成本高，但拦住的是执行本身 |

> **一句话记住** 输入过滤是「猜坏人长什么样」，输出编码是「让数据永远只是数据」。前者是黑名单的思路，后者才是白名单的思路——这在上一篇 SQL 注入里我们刚经历过一次同样的结论。

按这个顺序落地，成本从低到高：先确认所有输出点都做了与上下文匹配的编码，再给会话 Cookie 加 HttpOnly 与 Secure，最后在有条件时上 CSP。三层里最容易漏的是第一层，因为输出点往往散落在几十个模板里，而过滤函数只写一处。

## 七、自查：怎么在自己的站点上找这个问题

这一节是可复用清单，不涉及任何利用手法，只讲「从哪几个位置看」。

- 把所有把用户输入写回页面的位置列出来：搜索回显、错误提示、个人昵称、URL 参数渲染的文案。

- 在每个位置输入一个特殊字符，比如一个双引号，然后查看页面源码，确认它是被编码成了实体还是原样出现。

- 原样出现的地方标记为风险点，逐一确认是否做了与上下文匹配的转义。

- 检查会话 Cookie 是否带 HttpOnly、Secure 标记，检查响应头是否配了 CSP。

- 把这次确认过的位置记进检查表，下次上线新功能时优先看这几处。

*输出点比输入点重要：一个页面上可能只有三个输入框，却有二三十处回显位置，漏一个就等于没做。*

## 八、踩坑记录

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 弹窗不出现 | 输入被实体编码了，或落在了不能执行脚本的属性里 | 查看页面源码，确认输入落在 HTML 的什么位置 |
| 地址栏粘脚本没反应 | 特殊字符被浏览器处理掉了 | 不用地址栏手输，从页面表单提交或修改请求参数 |
| 浏览器拦截弹窗 | 浏览器的防弹窗策略 | 换浏览器或用页面内的可见变化作为验证信号 |
| 换浏览器后没变化 | 之前误以为是存储型 | 看刷新与换浏览器的差异，反射型换浏览器不会复现 |

## 九、小结

- XSS 的本质只有一句：用户输入被浏览器当成了代码。

- 反射型的三条判定：原样输出、脚本在 URL 里、刷新后不再触发。

- 弹窗是证据，不是目的；真正的风险面是「脚本能在这个页面上做哪些事」。

- 防护的重点在输出编码，其次是 Cookie 标记与 CSP，输入过滤只能算辅助。
